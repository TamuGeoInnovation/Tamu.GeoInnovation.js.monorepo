## What was built

Both decisions were built as asked, with three things to know:

1. **The settings are in Research Competitions, not Admin, Seasons.** The batch said Admin, Seasons, as my report 81
   put it. But the season's competitions and their deadlines are set in Research Competitions' **Competition settings**
   panel (#3037), with one Save, so the session choices and finalists dates are a third table there: **Sessions and
   finalists** (question 1).
2. **`season_competitions` needed a `runs` column.** Since #2948 a row has meant "the season runs this competition",
   and a season that runs every one has no rows. Saving the choice deleted and recreated them, so settings stored there
   would have been lost.
   - `runs` is set to 1 on every existing row (`WITH VALUES`).
   - A settings-only row has it empty.
   - Saving the competitions now marks `runs` and keeps settings.
   - **The deploy window:** production's current API counts every row as "runs". There are no settings-only rows until
     the new API writes them, so it is safe between migration and deploy.
3. **Session columns have no foreign keys.** SQL Server refuses several cascading keys between two tables (three
   `SET NULL` keys to `events`). A chosen session that no longer exists falls back to the `COMPETITION:` names, as an
   unchosen one does.

**For the 2026 season:**

## What this changes

<!-- What a reader needs to know. Why, not only what. -->

The rest of #3019, as decided (6A and 7A).

**Sessions, chosen on the season (6A).**
- **Where:** each competition's row of `season_competitions` (#2948) gains `sessionGuid` (the poster session, or the undergraduate presentation session), `graduateSessionGuid` and `awardsSessionGuid`.
- **Admin:** they're set in Research Competitions' **Competition settings**, under a new **Sessions and finalists** table, picked from the season's own sessions. That panel is where the season's competitions and deadlines are already set (#3037), so I put them there rather than in Admin, Seasons.
- **Who uses them:** the presentation and poster pages and the acceptance emails (#2985), through `competitionSession` and `awardsSession`. Each falls back to the `COMPETITION:` / `AWARDS:` names when nothing is chosen, or when the chosen session no longer exists. So 2026 reads as before.

**When finalists hear (7A).**
- `finalistsNotifiedAt` is set per competition in the same table.
- The poster and presentation pages show it in Central time, and leave the line out when it isn't set.
- **This is visible on production as soon as it deploys:** the typed "Saturday November 14th, 2026" line disappears until an admin sets a date.

**One design change that 6A needed.** `season_competitions` holds a row only for each competition a season runs, and none at all when it runs every one. Saving the choice also deleted and recreated the rows. Either would have lost settings stored there.
- **`runs`:** a new column, 1 on every existing row, keeps that meaning. A row that holds only settings has it empty, and `seasonCompetitions` counts only rows that run.
- **Saving the competitions** now marks `runs` instead of replacing rows, and removes only a row left with nothing.
- **A new endpoint,** `PATCH seasons/:guid/competition-settings` (`update:competitions`), saves the settings, refusing a session that isn't one of the season's. The panel sends it after the competitions, since both write those rows.
- **Session columns are plain ids, with no foreign keys.** SQL Server allows only one cascading key between two tables, and a missing session falls back to the names.

**The migration,** `AddCompetitionSettings1795487604412`:
- it adds the five columns, with `runs` filled `WITH VALUES`, so production's current API, which counts every row as "runs", keeps working between the migration and the deploy;
- its `down()` removes settings-only rows first, because the old API would count them as competitions the season runs.

`scrub.sql` keeps the new columns, which hold no personal data.
