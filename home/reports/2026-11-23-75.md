## What this changes

<!-- What a reader needs to know. Why, not only what. -->

The Ask to judge (#3183) and Ask for slides (#3113) emails skip a person already sent that email about that session in
the last ten minutes. Their guard was `RecentSends`, a map in each API process's memory, and production runs two copies
of the API, so a repeat that reached the other copy went out again. #3098 moved the session details email's guard into
a table both copies share; this gives all three emails that one table and one helper.

- **`SpeakerEmailClaim`** (`speaker_email_claims`): which email (`kind`: `session-details`, `slides-request`,
  `judging`), which session, which speaker, and when (`created`). A session's or a speaker's rows go with it
  (`ON DELETE CASCADE`). It replaces #3098's `SessionDetailsSend`.
- **`RepeatGuard`** (`speaker-edit/repeat-guard.ts`), provided and exported by `SpeakerEditModule`: `claim(kind,
  session, speakers)` and `release(claim)`, #3098's claim-then-check moved out of the session details email unchanged.
  Each claim's rows share one time and an id prefix, so two racing claims are ordered alike for every speaker; exactly
  one goes. Each kind is guarded on its own: being sent a session's details does not stop being asked for its slides.
- The three email services take a `RepeatGuard`; `RecentSends` is deleted (nothing else used it).
- **Migration** `AddSpeakerEmailClaims1795459774518` adds the table, copies every `session_details_sends` row into it as
  kind `session-details`, and drops `session_details_sends`; `down()` recreates it as #3098 made it and copies those
  rows back. `AddSessionDetailsSends1795448491167` is untouched. The old API reads `session_details_sends`, so the
  migration and the deploy go together.
- `scrub.sql` swaps `session_details_sends` for `speaker_email_claims`.
