## The design, as decided (B)

- **`SeasonCompetition`, table `season_competitions`:** `guid`, `created`/`updated` like every entity, `competitionType`
  (`nvarchar(50)`), `seasonGuid` (not null, `ON DELETE CASCADE`), **unique on (season, competitionType)**. A later
  per-competition setting is a column here.
- **`Season.competitions`**, one-to-many, **eager**, no cascade: every season the API loads carries its rows, so the
  form, the landing page, the deadlines and the submission checks read them with no new queries. The column is gone.
- **No rows = every competition**, as the empty column was. Saving all four stores no rows, so a competition added
  later runs too.
- **`setCompetitionTypes`** replaces a season's rows in one transaction (delete, then insert one per competition).
- **Interfaces kept:** `PATCH seasons/:guid/competition-types` takes `{ competitionTypes: [...] }` as before; the admin
  section, the form and the pages are unchanged. Only the shared helpers in `gisday/common` read rows instead of the
  string (`competitionTypesValue` now returns the rows to store).

**Why eager is safe here:** several API paths pass a loaded season as a `where` value (`{ season: activeSeason }` in
the speaker provider, the season clone, and others). Those seasons already carry a loaded `days` array and work in
production. A test now pins that a season carrying `competitions` still builds as a `where` value in TypeORM's real
query builder. Cloning makes a fresh season (`incrementYear`), so no rows move to it. A new season starts with none,
as its deadlines start open.
