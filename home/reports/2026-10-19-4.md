## Cause
Both lookups in `EventService` (`?lot=`-style and `?feature=` links) called `layer.queryFeatures({...})` with a query of
their own. In `@arcgis/core` 5.1.27, `FeatureLayer.queryFeatures` sends a query it is given unchanged; only
`layer.createQuery()` carries the layer's `definitionExpression` (and subtype filter). Confirmed on a real client-side
layer in Vitest: the explicit query returned the `H/C` and the `M/C` space; `createQuery().where` was `Spc_Type = 'M/C'`.

## Decision: let ArcGIS apply the filter
A helper, `queryDrawnFeatures`, starts from `layer.createQuery()` and ANDs the lookup's own `where` onto it; both lookups
use it. One copy of the rule, and it covers a filter however it was set (definition, builder choice, subtype).
- **`?feature=` links follow the same rule:** a link selects only what the map shows. A popup's copy link carries the
  builder settings that produced the filter, so a link copied from a map still selects its feature.
- **Sidebar search picks follow it too** (they use the same object-id lookup).
- **Deliberate:** a link shared before a map's filter changed now selects nothing (e.g.
  `?feature=motorcycle-parking-space:26692`). Stated in the issue comment and the PR body.
- A lot link matching drawn and undrawn features now selects a drawn one: `?lot=100j` selects 32270, an `M/C` space.
