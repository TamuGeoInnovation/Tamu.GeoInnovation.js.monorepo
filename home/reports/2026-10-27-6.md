# home: batch 6 report (aggiemap: #2472, the dev server stalls at the dependency optimizer)

From `home` (the Listener chat), Tuesday 27 October 2026. Batch from `work (aggiemap)`. An investigation; nothing pushed.

## The answer

**It reproduces on demand, and it is `--poll` combined with an empty dependency cache.**

- With `--poll`, the dev server's Node process uses about two cores continuously, even when idle.
- When Vite has to build its dependency cache, which happens on a fresh `.angular` cache or after a dependency change, that
  busy process never drives esbuild through the bundle. The log stops at `[optimizer] bundling dependencies...` for good.
- Without `--poll`, the same cache builds in 37 s. With a warm cache, `--poll` loads fine.
- `UV_THREADPOOL_SIZE` is not the lever: 64 and 1024 behave the same.

**The second volume is a red herring.** The volume itself doesn't matter: what matters is that the new volume, and the
checkout with it, had no warm cache. The shared `tamu-js-dev-nm` setup works because its checkout's `.angular` cache was
built long ago.

No one-line fix fell out, so nothing is pushed. Removing `--poll` stops the stall but loses edits made on Windows (trial 6).
There is a workaround, with a recommendation to make it the documented command; see the end of this report.

## What it is stuck on

During a stall (`--poll=2000`, empty cache), reading `/proc` twice, 10 s apart:

- **the Nx executor's `node` process (the dev server) used about 21 s of CPU in those 10 s**, two cores flat out;
- **`esbuild --service` used 0.01 s**: idle, not bundling.

So no dependency is "the one". esbuild is not working on any package. The Node process that has to drive it, and collect
its result, is saturated. That process stays at 155-188% CPU with `--poll` even with a warm cache (trials 4 and 5), and
idles below 1% without it (trial 3). The polling watcher is what keeps it busy. `vite:deps` names no package, because the
bundle never starts producing output. The cache folder is left holding only its `package.json`, as in both of this
morning's stalls (`deps_temp_b10fb95c`, `deps_temp_c151dcbe`).

`UV_THREADPOOL_SIZE` fixed #1955 when its cause was the thread pool; this is CPU on the event loop, so a larger pool cannot
help (trial 4b). The lab's 24 CPUs against home's 20 make no difference to that: both machines stalled the same way today.

## Questions for the director (aggiemap)

1. **What to document.** No code change fixes it within this batch.
   - **A. Prime the cache, then poll ← recommended**: a fix that needs no code change and keeps edits from Windows working.
     1. Start the server once without `--poll`, and wait for `dependencies optimized` (about 40 s after the first page
        request).
     2. Stop it, and start the normal `--poll=2000` command. It reuses the cache, kept in the checkout's `.angular`, and loads
        in seconds (trials 4 and 5).
     3. Repeat only after a dependency change.

     It would go in CLAUDE.md beside the dev server command and in #2472.
   - B. Drop `--poll` and edit inside the container (or a WSL clone) instead, so file events reach the server. This is a
     larger change to how everyone works.
   - C. Find what the polling watcher watches (it may include `node_modules`) and narrow it. That is the real fix, but an
     investigation of its own; a new issue.

## Findings

- With `--poll=2000`, the dev server costs one and a half to two cores even when nothing is happening (trials 4 and 5). That
  is worth knowing when a dev server and a check share a machine ("Nothing heavy beside a run").
- Nothing was left running. The trial containers and their cache volumes were removed. `tamu-js-2453-nm` and
  `C:\TAMU\wt-2453` are still here from batch 5.
