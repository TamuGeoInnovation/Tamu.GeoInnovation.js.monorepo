## Two faults found while widening the change

1. **`EventService.selectFeatureByFieldMatch` matched field names case-sensitively.** With the lot keys in lower case,
   `?lot=100j` on Visitor Parking and Motorcycle Parking no longer matched their own `LotName` layers. It fell through to
   the main map's Lot 100j, which is #1969 returning: `lot-links.spec.ts` was 4 red, and 7 unit tests were red. It now
   ignores case. A new unit test was red on the old matcher, and 36 of 36 pass with the fix. #2786 lower-cased the
   `?bldg=` keys the same way, but no event map keys a layer on a capital-N `Number`, so nothing broke there. It is a
   latent fault #2786 could have exposed and did not, found by widening the change, not caught by a check.
2. **The garage popup shares the lot popup's template.** Once that template read `lotname`, garages, which still come from
   the old service as `LotName`, opened with no name. The garage search smoke failed, and the existing garage unit test
   went red. The template now reads either spelling, and a lot test covers the new one.

## The #2786 "regression": what happened, and the lesson

Dev's buildings were reported dead, so I stopped. I then measured a cause and sent it, sent a second, and retracted
both. **Layer 0 works on dev.** Every numbered building in view answers a hit test, 105 of 105, and no unnumbered
structure does, 0 of 73, which is what `number IS NOT NULL` is for.

**What went wrong, in the director's terms, because we both did it independently: we sampled the population the filter
exists to remove, and then measured the filter.** Every probe took the first features from
`layer.queryFeatures(geometry: view.extent)` with no `where`. Those come in object id order, and the low ids are the
unnumbered structures. So "1=1 hits, any filter misses, every hit has null attributes" was the unnumbered rows being
drawn with their genuinely empty attributes, and then correctly filtered out. A test whose sample is taken from the rows
the filter removes will confirm whatever the filter does. The fixtures in this batch's checks are therefore the rows the
filter keeps, asked of the service with the same filter, or buildings chosen by name.

**What caught it was the new hit-test assertion.** I added it to `building-clicks.spec.ts` because the click fallback
(PR 2718, #2785) can answer a click for a layer that is not hit-testable. Run against dev, it passed 8 of 8, while my
probe in the same page said 0 of 18. That contradiction exposed the sampling flaw. The assertion stays: the layer itself
must answer `view.hitTest` at every building clicked, not only the popup naming it.

The maintainer's own report, no popup on any building on dev in his browser, is **still unexplained**. Neither I nor the
director reproduced it. The director is not probing further without a specific building from him, and neither am I.
