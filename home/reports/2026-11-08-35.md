## What was found

The check, run red on unfixed code, found two more services that a development build cannot use while
production serves them. So nine layers were dead, not six:

| Layers | Service | On the development server |
| --- | --- | --- |
| Dismount Zones, City Bike Lanes and Routes, Campus Bike Lanes, Bike Fix Stations, Bike Racks, EV Charge Stations | `TS/BikeMap` | 499 "Token Required" |
| Accessible Building Entrances | `FCOR/ADA_120717` | the service is there with no layers, so layer 0 answers 404 |
| Emergency Phones, Single Occupancy Restroom Locations | `FCOR/MapInfo_20190529` | the service is there with no layers |

All nine were on `allowedLayerFailures` under #1005. Development's `allowedLayerFailures` and `allowedServiceFailures`
are now both empty.

## What was built

1. **The pin.** `READ_FROM_PRODUCTION_ON_DEVELOPMENT` moved from the spec into `connections.ts`, is exported, and
   now does the pinning. The 19 Transportation services that were pinned by writing `arc.ts.tamu.edu` into their URLs
   are written like any other, and the list pins them. So there is one way to pin, not two. Added to the list:
   - `bikeMapUrl`, `bikeRacksUrl`, `accessibleUrl` and `inforUrl`;
   - `lactationRoomsUrl` and `natureRxUrl`, which already read production everywhere. They are listed only so that
     their layers are marked too.
2. **The check, in `services.spec.ts`.** On dev, it fails when a service:
   - answers 499 or 404 while production's counterpart answers;
   - or, as a service root, lacks layers that production has (this is what found MapInfo).

   Its message names the list to add the service to, and no allow-list entry covers it.
3. **The marker.** `markReadFromProduction()` gives each source drawn from a listed service the list's reason, as
   `readFromProduction`. It also marks a group when any of its children is marked, because Sustainable
   Transportation shows as one row in the list. It runs where all sources pass:
   - `factory()` for the main map;
   - `eventLayerSources()` for the event maps.

   Where the host is production's it does nothing, so the label cannot appear on production. The Layers list shows
   a small **production data** label after the title, with the reason on hover.

## Three traps, for whoever does the next one of these

- **Esri's layer constructors drop properties they don't know.** A new `LayerSource` property never reaches the
  layer list unless it is set on the built layer afterwards. `generateLayer` now does that for `readFromProduction`,
  as was already done for `listHeading`. `listNote` probably has the same problem; I did not check.
- **The local build (`environment.ts`) reads production on purpose.** A capture of "dev" behaviour needs
  `--configuration=development`, which my first "after" image did not have.
- **My first two red runs passed.** A Python edit wrote a literal backspace where `\b` belonged in the check's
  regex, so it never matched. Neither the typecheck nor lint catches that. Only running the check red did.
