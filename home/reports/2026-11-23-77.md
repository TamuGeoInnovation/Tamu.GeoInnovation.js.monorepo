### The migration's exact SQL, for the production script

`up()`, three statements in order:

```sql
CREATE TABLE "sessions_filter_backfill" (
    "placeGuid" nvarchar(255) NOT NULL,
    "before" nvarchar(max),
    "after" nvarchar(max) NOT NULL,
    CONSTRAINT "PK_sessions_filter_backfill" PRIMARY KEY ("placeGuid")
);

INSERT INTO "sessions_filter_backfill" ("placeGuid", "before", "after")
SELECT "p"."guid", "v"."before",
       CASE WHEN "v"."list" = N'[]' THEN N'["sessions-filter"]'
            ELSE LEFT("v"."list", LEN("v"."list") - 1) + N',"sessions-filter"]' END
FROM "places" "p"
INNER JOIN "seasons" "s" ON "s"."guid" = "p"."seasonGuid"
CROSS APPLY (
    SELECT CAST("p"."visibilitySettings" AS nvarchar(max)) AS "before",
           LTRIM(RTRIM(COALESCE(NULLIF(CAST("p"."visibilitySettings" AS nvarchar(max)), N''), N'[]'))) AS "list"
) "v"
WHERE "s"."year" < (SELECT MAX("year") FROM "seasons" WHERE "active" = 1)
  AND "v"."list" LIKE N'[[]%]'
  AND "v"."list" NOT LIKE N'%"sessions-filter"%'
  AND EXISTS (
    SELECT 1
    FROM "events" "e"
    INNER JOIN "event_location" "l" ON "l"."guid" = "e"."locationGuid"
    WHERE "l"."placeGuid" = "p"."guid" AND "e"."seasonGuid" = "s"."guid"
  );

UPDATE "p" SET "visibilitySettings" = "b"."after"
FROM "places" "p"
INNER JOIN "sessions_filter_backfill" "b" ON "b"."placeGuid" = "p"."guid";
```

`down()`, two statements in order:

```sql
UPDATE "p" SET "visibilitySettings" = "b"."before"
FROM "places" "p"
INNER JOIN "sessions_filter_backfill" "b" ON "b"."placeGuid" = "p"."guid"
WHERE CAST("p"."visibilitySettings" AS nvarchar(max)) = "b"."after";

DROP TABLE "sessions_filter_backfill";
```

The table stays after `up()` so that `down()` can work. A later migration can drop it once no rollback past this one is
wanted, as #3269 does for `session_details_sends`. I have not filed that, in case the director prefers to keep the table.

## What this changes

<!-- What a reader needs to know. Why, not only what. -->

A hybrid or virtual session's QR code opens its check-in page with the session's code in the address (`?checkin=<code>`), and the address kept it. So the code went into Google Analytics' page views, the browser's history, and any link copied from the address bar.

**Who reports the page view.** The issue proposed removing the code from inside the app, before angulartics2 sent its page view. That doesn't work here, because angulartics2 sends nothing on this site. Its Google Analytics provider calls `ga()` (analytics.js), and gisday-angular never loads that. The page view Google records is gtag's own: `gtag('config', id)` in `index.html` sends it with the address it finds, and it runs outside Angular. A `router.navigate(..., { replaceUrl: true })` in the component can't be relied on to beat it.

**The fix.**
- `apps/gisday-angular/src/index.html`: a small inline script, placed before the Google tag's script.
  - It takes `checkin` out of the address with `history.replaceState`, keeping the rest of the address and the hash.
  - It keeps the code in this tab's `sessionStorage`, under `gisday-checkin-code:<path>`.
  - It runs before the tag is configured and before the app starts. The code is therefore never in the address that Analytics, the router or the history see.
- `event-checkin.component.ts`: reads the address's code first (unchanged), then the code kept for its own path.
- Signing in still works. Auth0 comes back to the same tab, which still has the code, and the existing once-per-scan sign-in key is unchanged.
- `CHECK_IN_CODE_KEPT` in `@tamu-gisc/gisday/common` names the storage key; `index.html` uses the same string.

**Why `sessionStorage`.** If storage is refused, the page shows its existing "This link has no check-in code" message, and the attendee can scan again.

Nothing changes in the API or in the code itself, which still covers the whole session, by design.

## What this changes

<!-- What a reader needs to know. Why, not only what. -->

On a past year's Sessions page (for example txgisday.org/seasons/2025/sessions), the **Organizations** filter said "There are no organizations.", although that year's sessions name where they were held. Since #1826 the filter lists only the organizations with **Sessions Filter** ticked. No past season's organization had that new setting, and each season has its own copies of its organizations, so ticking this year's in Admin never reached them.

**The fix** is a one-time migration, `TickPastSessionsFilters1795477533912`, so it runs the same way on every database.
- **What it ticks:** **Sessions Filter**, on each past season's organizations that hosted at least one of that season's sessions. A past season is one whose year is before the active season's.
  - "Hosted" means a session of that season whose location is that organization.
  - An organization with no sessions that year stays unticked, so the filter only offers choices that return sessions.
  - The current season, and any later one, is left alone: its organizations are ticked by hand.
- **How it ticks:** `"sessions-filter"` goes on the end of the `simple-json` list. An empty value becomes `["sessions-filter"]`. An organization already ticked, or whose settings aren't a JSON list, is left as it is.
  - Plain string operations, not `JSON_MODIFY` or `OPENJSON`. SQL Server doesn't promise to evaluate an `ISJSON` guard first, so an odd value could otherwise fail the whole migration.
- **Undoing it:** `down()` puts back only what `up()` changed. `up()` records each organization it ticked, with its settings before and after, in a new table, `sessions_filter_backfill`.
  - `down()` restores "before" only where the settings are still exactly "after". An organization edited in Admin since keeps its edit.
  - The API never reads that table, and `scrub.sql` skips it.
- **The test:** a smoke test asks the API for the most recent past season and where its sessions were held. It checks that year's page offers at least one of those organizations, and only those.

The production data checked on 23 November is the reason this is safe:

| Season | Sessions | Organizations | Hosted sessions | Ticked now |
| --- | --- | --- | --- | --- |
| 2023 | 66 | 10 | 8 | 0 |
| 2024 | 87 | 10 | 10 | 0 |
| 2025 | 114 | 12 | 11 | 0 |

Every session's organization belongs to its own season, and each organization's settings are either NULL or a JSON list.
