## Not as the batch said: the profile email is not on `speaker_email_claims`

The batch said a new claim `kind` would need no migration. That's right about `kind`, but `speaker_email_claims.session` is **NOT NULL**, and the profile email is about no session. Putting it on the claims table needs:
- that column made nullable, so a migration;
- and so a production step (`migrate-prod-3326.ps1` in the operations repository) before the image.

Overnight, the conservative choice was no schema change. So:
- **The profile email's link is its claim.** The link row is saved first, with its id and time set as a claim's are.
  - It stands only if it is the speaker's earliest profile link of the last `REPEAT_SEND_MINUTES`, by `RepeatGuard`'s `firstOf` (now exported), so every copy of the API agrees.
  - A loser is deleted and skipped, with the same reason as before.
- **A link whose email fails is deleted,** so the admin may retry at once, as the other three allow. Before, a failed send left its link and blocked a retry for ten minutes. That's a behaviour change, and a fix.
- **`sendEach(repeats, emails, how)`** beside `RepeatGuard` is now the one loop the three session emails use, behind their existing interfaces. The profile email doesn't use it, because its claim is its link, which it also needs for the email's URL.

## What this changes

<!-- What a reader needs to know. Why, not only what. -->

The judging, Ask for slides and session details emails each wrote out the same send loop: claim, send, record, and release on failure, guarded by `RepeatGuard` (#3098, #3260). The profile email (`sendLinks`) guarded another way. It counted the speaker's profile links of the last `REPEAT_SEND_MINUTES` and made one only if there were none. Two sends racing, in one copy of the API or in two, both counted none, and the speaker got the email twice (#3326).

**What changed**
- **Two racing sends of the profile email send it once.**
  - The speaker's new profile link is now the claim: it is saved first, with its id and time set as a claim's are.
  - It stands only if it is the speaker's earliest profile link of the last `REPEAT_SEND_MINUTES`, by `RepeatGuard`'s own `firstOf`, now exported. Otherwise it is deleted and the speaker skipped, with the same reason as before.
  - A link whose email fails is deleted too, so the admin may try again at once, as the other three emails allow. Before, a failed send left its link behind and blocked a retry for ten minutes.
- **`sendEach(repeats, emails, how)`**, beside `RepeatGuard`, is the loop the three session emails each wrote out. All three use it, behind their existing interfaces; their own tests pass unchanged.

**Why the profile email is not on `speaker_email_claims` itself,** as the issue proposed:
- A claim's `session` is `NOT NULL`, and the profile email is about no session.
- Putting it there needs a migration that makes that column nullable, and so a production step (`migrate-prod-3326.ps1`) before the image.
- The links table already holds a row for every profile email, written before it goes, so the same earliest-claim rule applies there with no schema change.
- Moving it onto the claims table later is a question for the maintainer.
