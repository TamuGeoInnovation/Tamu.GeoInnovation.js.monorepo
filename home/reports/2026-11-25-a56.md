## 1. The retry

**`retry_once <label> <command...>`** runs the command as a step and, if it fails, once more after 5 s
(`CHECK_RETRY_DELAY`). The log says why, in a line ending "(#3695)". A second failure returns non-zero, so the check
still exits 3. It is never a loop.
- **All three reads of `/src` go through it:** the clone and both fetches. The fetches cross the same file sharing,
  and would fail the same way on a volume that already has its clone.
- **A clone that fails part-way removes its `.git` first** (`clone_src`), so the second try can clone into the volume.
- **The checkout step is not retried.** It reads only the volume, not `/src`.
- **It runs inside the container, which is POSIX `sh` (dash in `node:24.22.3`).** So `retry_once` is POSIX, and it
  is passed in with `declare -f`, as `unknown_projects` already is.
- **Proven in dash:** run in that image's `sh`, it passed on the second try, and failed after a repeated failure.

## 2. What exit 3 now says

`setup_advice`, beside `memory_advice`, after the run:
- **Any exit 3:** "the check stopped before checking anything, because the container could not read the branch from
  this checkout (clone, fetch or checkout)."
- **When the log shows `Cannot allocate memory`:** also that this was Docker's file sharing reading the Windows drive,
  not the branch; that each read was tried twice; and to run the same command again.
- **A different exit 3** (for example a branch that does not exist) does not blame file sharing.

## What this changes

`scripts/check-in-volume.sh` runs its check in a container that reads the checkout at `/src` through Docker's file
sharing from the Windows drive. That read fails now and then before anything is checked. On 25 November a clone
stopped with this, and the check exited **3**:

```
warning: error reading directory '/src/.git/objects/08/': Cannot allocate memory
```

The same branch checked a minute later gave Exit 0. Exit 3 said nothing, so it read as a broken branch or a mistyped
name.

- **One retry.** The clone and both fetches go through `retry_once`: a failure is tried once more after 5 seconds,
  and the log says why. A second failure still exits 3, never a loop. A clone that fails part-way removes its `.git`
  first, so the second try can clone.
- **Exit 3 explained.** After the run, an exit 3 says the check stopped before checking anything. When the log shows
  `Cannot allocate memory`, it also says that was Docker's file sharing, and to run the same command again. This sits
  beside the memory-kill advice (#3000) and the full-disk guard (#3365).
- **Not narrowed.** The clone is still whole. The volume keeps the full clone on purpose, for the speed-up #1402
  measured.

The `CLAUDE.md` entry #3695 also asks for is not in this pull request. PR 3676 is open on the same section, and two
additions to that list conflict (#2002), so it follows once 3676 merges.
