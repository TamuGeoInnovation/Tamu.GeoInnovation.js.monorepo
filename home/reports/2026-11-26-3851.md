# #3851 (a travel-option change erases the route), 11:02 PM Central, 26 November

**Not shown to happen, so no branch.** #3851 asked me to prove the path first; it does not reproduce, and the code says why.

## By hand
- **The build:** local production, with a route solved from `/map/d/trip?stops=30.6150,-96.3500@30.6150,-96.3300` (1.53 miles). `route-segments-layer` holds **2** graphics.
- **The changes:** options that keep the travel mode. I chose **Leave at**, read the layer at +250 ms, +1 s, +3 s and +6 s, then changed the time with the picker, then chose **Leave now**. The layer held **2 graphics at every reading**, and the panel kept 1.53 miles.
- **The phone** (`/map/m/trip`, iPhone 13 size): the route draws, and its trip planner has **no time menu** (`tamu-gisc-trip-planner-time-picker` is used only in the desktop mode picker). So there is no same-mode option to change there.

## Why it does not happen
The settings handler does run `_TravelOptions.next(res)`, then `clearRoute()`, then `executeTripTask()`, which returns early for the same modes. But `currentResult$` is `TravelOptions.pipe(switchMap(() => getTripResultForTravelMode()))`, so **every travel-option emission re-reads the results and calls `drawRoute` again**. `drawRoute` draws inside `moduleProvider.require(...).then`, which is asynchronous, so the redraw lands after the synchronous `clearRoute()` and the line comes back.

**The one gap:** `currentResult$` uses `refCount`, so it redraws only while a component subscribes. I found no screen where options can change with no directions component subscribed.

## So
- **#3851:** close it as not reproducing, with this evidence. Its `clearRoute()` is redundant but harmless, and removing it is a cleanup, not a bug fix.
- **#2846** is then unexplained again: neither its own check (60 of 60) nor this path reproduces it. The trips since 11 November with #2851 and #2844 in are the evidence that it is gone.
