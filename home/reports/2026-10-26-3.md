## 5. The cluster's deployments (read only; nothing changed)

Read in the maintainer's private deployment configuration. **The names, paths and storage details are left out here because
this branch is public**; the director can read them there.

- **gisday-nest, both sites:** each mounts a shared, read-write volume at its `APP_DATA`, and the volume already holds files
  root wrote. No deployment sets a `securityContext`. **These need the change below.**
- **geoservices-nest:** mounts nothing and writes nothing. Nothing needed.
- **mailroom-nest and mailroom-helper-nest:** not in that configuration; it only names them as a URL. They write nothing, so
  their files need nothing wherever they run.

What the two GIS Day API deployments need (the maintainer's change):

1. A pod `securityContext` with `runAsUser: 1000`, `runAsGroup: 1000` and `fsGroup: 1000`. The configuration already does this
   for another workload on the same kind of shared volume.
2. **Whether `fsGroup` changes the owner of the files already on that volume depends on the storage's CSI driver.** It does
   only when the driver's `fsGroupPolicy` is `File` (`kubectl get csidriver <driver> -o jsonpath='{.spec.fsGroupPolicy}'`).
   If it is not, give the volume to uid 1000 once: an `initContainer` running as root with `chown -R 1000:1000 <APP_DATA>`, or
   a one-off Job.
3. Deploy that with or before the new image. With the image alone, speaker, organization and place uploads and Copy to another
   site fail with `EACCES`.
4. The website pods that read the same volume are unaffected: the API writes files `644` and folders `755`, as before.
