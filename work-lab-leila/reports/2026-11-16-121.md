## The photo, and where the 413 comes from

- **The photo:** a made-up gradient JPEG, **9,000 x 6,000 pixels, 1,497,364 bytes**.
- **The 413 happened locally, as on production.** The API answered "The photo is too large in pixels: 9000 x 6000. The most
  is 8000 a side and 40 megapixels."
  - It comes from the API itself: `refuseUnsafeImage` in `libs/gisday/platform/data-api/src/lib/assets/image-upload.ts`,
    called from the speaker provider's `_saveImage`.
  - That function reads the pixel size from the image's header and throws `PayloadTooLargeException`.
  - nginx (`client_max_body_size 110m`) and the 5 MB file limit play no part.
- **After, Update saves.** The whole request was 21 KB.
- **The stored file is not 1,600 on its longest side: it's JPEG, 1,260 x 840, 39,533 bytes,** measured from the file in the
  API's storage.
  - The browser shrinks the photo to at most 1,600 a side.
  - The API then fits every speaker photo to 840 on its shorter side (`SPEAKER_PHOTO_FIT`).
  - That is the existing design, not a bug, and the release note says so.
