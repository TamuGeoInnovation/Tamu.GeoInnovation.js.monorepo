## 1. The design: an internal network plus an egress proxy

| Option | Verdict |
| --- | --- |
| `iptables` rules in `DOCKER-USER` | **Not chosen.** On Docker Desktop the rules have to go inside its VM. They are lost when it restarts or updates and must be re-applied from outside, and on Linux they are a second, different mechanism. More moving parts, and two of them. |
| **An internal Docker network and an egress proxy** | **Chosen.** No host rules at all, so it is the same on Docker Desktop (WSL 2) and a plain Linux host. It cannot be bypassed from inside: the network has no route out, and the container has no capabilities to change that. |

How it fits together:

- **`tamu-agent-internal`** is created with `docker network create --internal --subnet 172.31.250.0/24`. A container on it has **no route out
  and no outside DNS**.
- **`tamu-agent-egress`** is a Squid proxy on that network (`172.31.250.2`) and on Docker's default bridge. It is the only way out.
  - It accepts clients only from the agent's subnet.
  - It allows **ports 80 and 443 only**, and CONNECT to 443 only.
  - It **refuses** `0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.168/16, ::1, fc00::/7, fe80::/10`. Squid checks the address it
    actually connects to, so a public name that resolves to a private address is refused too.
  - It keeps no cache and adds no forwarding headers.
  - It runs as `proxy` with **every capability dropped**, `no-new-privileges`, 512 MB and 1 CPU.
  - It **logs every connection to `docker logs tamu-agent-egress`**. `-N` keeps Squid's output on the container's, since `--foreground`
    sent it to `/dev/null`. The ICMP pinger is off, as it cannot work without capabilities.
- **`run-agent.ps1`**:
  - **`Confirm-Egress` runs before every job.** It creates the network, starts the proxy and connects it to the network, each only if
    missing. A restart of Docker or the machine while the supervisor runs is recovered on the next job, and the proxy also has
    `--restart unless-stopped`.
  - The agent's container goes on the internal network with `AZP_PROXY_URL`, `HTTP(S)_PROXY`, `http(s)_proxy` and `NODE_USE_ENV_PROXY=1`.
  - **Containers are now named after their agent** (`tamu-build-agent-lab-1`). My first test collided with the maintainer's running
    `tamu-build-agent`; it was refused at `docker create` and did nothing to his.
  - `-AgentName` also accepts `<machine>-test`, as batch 68 asks.
- **`start.sh`** passes `--proxyurl "$AZP_PROXY_URL"` to `config.sh` when it is set, so the agent's own connection and the tasks it runs use
  the proxy.

**One difference from the batch's expectation: "DNS still resolves" does not hold for outside names**, and I have left it that way. Docker
gives an `--internal` network no outside DNS. Nothing needs it: a client using the proxy sends the name to the proxy, which resolves it. That is
true of curl, git, npm, Node's own `fetch`/`http` with `NODE_USE_ENV_PROXY`, and the agent. **It also closes DNS as a way out**: with outside
DNS, fork code could leak data through lookups of names it controls, which no proxy would see. See question 1.

## Questions for the director (security)

1. **Outside DNS stays off inside the agent's container?** Options: (a) leave it off, as built: nothing needs it, and it closes DNS
   exfiltration; (b) add a DNS forwarder on the internal network. **Recommendation: (a).** If a pipeline task turns out to need local
   resolution, it will fail with *Could not resolve host* and name the tool, and we can decide then.
2. **The proxy allows any public host on 80/443.** It could be narrowed to an allow-list (npm, GitHub, Azure DevOps, Nx Cloud, nodejs.org, the
   Azure blob hosts the Cache task uses). That would stop fork code reaching the internet at large, but break the first time a dependency
   comes from somewhere new. **Recommendation: not now.** The goal was the local network, which is closed. Revisit when the agent takes real
   jobs, using the proxy's log of what jobs actually reach.
