## The answer

**Yes, a lost tile can be seen, through a public, documented property: `FeatureLayerView.hasAllFeaturesInView`.**

- **Esri documents it for this case:** "The hasAllFeaturesInView property will be `false` if some queries failed to
  execute" (`views/layers/FeatureLikeLayerView.d.ts`, since 4.29). It's reactive, so it can be watched.
- **It does see these failures, though they arrive as HTTP 200.** On 10 production loads, three signals agreed on
  every load, the clean ones included:
  - the error bodies on the wire;
  - the SDK's own `Failed to load tile <id>.` errors in the console;
  - `hasAllFeaturesInView === false` on exactly the layer views that lost a tile, and on no other.
- **And it stays false.** About 6 to 8 seconds after `ready`, every layer view stops `updating`. A layer that lost a tile
  then sits settled with `hasAllFeaturesInView: false` for as long as I watched (a minute). That's #2785 exactly: the
  click fallback asks only layer views that are `updating`, so it stops helping at the moment the fault becomes
  permanent. `hasAllFeaturesInView` is the property that keeps telling the truth.

**So #2785 is a small change.** In `queryPopupLayersAtClick`, also ask a layer whose view is not suspended and reports
`!hasAllFeaturesInView`, not only one that is `updating`. A click on a fully drawn map still asks nothing.

## 1. How a failed tile reaches the SDK

From the installed source (`@arcgis/core` 5.1.27, minified; the names are the SDK's own):

- **The worker turns an error body into a failed tile.** `views/2d/layers/features/sources/FeatureSource.js` loads each
  tile through its strategy and, on a rejection, sends `{type: "error", tile, error}` to the main thread.
- **The main thread keeps a log per tile.** `views/2d/layers/features/FeatureSourceEventLog.js` records each tile's
  last event. On `error` it emits an `error` event and calls
  `Logger.getLogger(this).error("Failed to load tile <id>.", {error})`.
- **`hasAllData` is false while any tile's last event isn't `loaded`.** It's internal, but the public layer view
  (`views/2d/layers/FeatureLikeLayerView2D.js`) builds three documented properties from it:
  - `hasAllFeaturesInView`: visible, not suspended, `hasAllData`, and no display filter that limits the query;
  - `hasAllFeatures` and `hasFullGeometries`, which also need the layer to have queried everything. The buildings layer
    queries by tile, so these are false anyway and no use here.
- **The exception it documents doesn't apply to us:** a display filter (`displayFilterInfo`) on a large layer also makes
  `hasAllFeaturesInView` false. **No layer in `libs/` or `apps/` uses a display filter** (`git grep displayFilter`: 0
  files), so for us false means a failed query.

**What doesn't help:**
- **`updating` and `dataUpdating`** both go false once the tiles are settled, failed or not.
- **The layer list's `ListItem.error`** reflects a load error, not a tile.
- **The event log's `error` event** is internal (`eventLog` isn't public).
- **`esriConfig.log.interceptors`** is public and does see `Failed to load tile` with the tile's id, but Esri says "the
  module name, message and detailed content of log messages is not considered stable" (`config.d.ts`). A fallback, not a
  foundation.

## 2. Would a retry be better?

**A retry fixes more**, as you say: a lost tile is missing from the drawing, not only from the hit test. On load 2, the
layer view held 101 buildings in view before a refresh and 114 after; on load 10, 81 then 114. That's 13 and 33
buildings simply not on the map.

**The one supported way to make a layer ask again is `layer.refresh()`, and it's blunt.** On 7 production loads that
had lost a tile, I called `refresh()` on the affected layer in a throwaway browser:

| What I measured | Result |
| --- | --- |
| Requests the refresh sent | **all 12 tiles** of that layer, every time, not just the lost one |
| The layer view's features in view, during the refresh | **fell to 0** every time (7 of 7), then came back |
| Time to settle | about 2.5 s |
| Complete afterwards (`hasAllFeaturesInView`) | **4 of 7** |
| Lost a tile again, during the refresh itself | **3 of 7**, each matched by an error body on the wire |

- **The refresh is exactly as reliable as a load,** since it's 12 more queries at today's rate, and `hasAllFeaturesInView`
  read correctly after every one. (My first attempt showed a mismatch; that was my script sampling before the refresh
  had settled. The second, which waited, matched 7 of 7.)
- **It throws away what's drawn.** The features in the view dropped to zero while it ran, so a visitor would likely see
  the layer blink. I measured the layer view's count, not pixels.
- **So "refresh on `!hasAllFeaturesInView`, a bounded number of times" is possible with supported calls.** But it
  re-asks all twelve tiles to recover one, and blinks the layer each time.
- **I found no supported per-tile retry.** The SDK itself never retries a tile: nothing in the feature strategies
  mentions a retry.

**A request interceptor isn't a clear way in either.**
- The worker factory sets `request.interceptors = []` and `log.interceptors = []` in the configuration it gives workers
  (`core/workers/workerFactory.js`), so a page's interceptors aren't copied into workers.
- Playwright attributed all 36 of a load's basemap queries to the page, not to one of the 8 workers. So the queries may
  be sent through the main thread, where an interceptor would see them. But **I couldn't prove that without changing the
  application**, and the batch rules that out. Whether `esriConfig.request.interceptors` sees these queries is an open
  question, and the first thing to test if anyone takes the interceptor route.

## 3. What else trusts a settled layer view (named, not fixed)

**In the application:**
- **`queryPopupLayersAtClick`** (`libs/maps/esri/src/lib/services/map/click-query.ts:30`): asks only layer views that are
  `updating`. #2785.
- **`view.hitTest` itself:** finds only what a layer view has drawn, so a lost tile is unclickable, which is why the
  fallback exists.
- **The layer list** (`libs/maps/feature/layer-list/.../layer-list-item.component.ts`): shows `updating` and `error`
  from Esri's `ListItem`. A layer with a lost tile shows as finished and healthy.
- **`whenBasemapDrawn`** (`libs/maps/feature/basemap/.../basemap-gallery.service.ts:668`): waits for the basemap's layer
  views to stop `updating`. That's harmless (it only ends a spinner), but "drawn" there means "settled", not "complete".
- **The legend** (`libs/maps/feature/legend`) reads no layer-view state at all. It keys symbols from renderers, so it's
  unaffected.

**In the smoke suite and tools:**
- **The map probe's `ready` and `drawing`** (`map-probe.ts`): `drawing` is `MapView.updating`. Both go true/false
  whatever the tiles did. Everything that waits on them waits for "settled":
  - `kiosk.spec`, `popup.spec`, `selection.spec`, `layer-order.spec`, `legend.spec` and `map-layers.spec`;
  - `test/visual/pages.spec.ts`, `tools/visual-baselines/capture.mjs`, `tools/builder-inventory/inventory.spec.ts`.
- **The probe's `featureCount` asks the service** (`layer.queryFeatureCount`), not the layer view. So **every check that
  counts features passes on a map that lost a tile**, because the server still has them all.
- **`map-layers.spec`'s "Drawn" check** asks the layer view for features in the extent and needs only one with a symbol.
  A lost tile among twelve passes it.
- **Captures:** a screenshot or a visual baseline taken after `drawing === false` can record a map with a missing tile.
  A baseline taken that way becomes the reference later captures are compared with.
- **`paint.spec`** counts painted pixels, and a missing tile of buildings may still clear its threshold. I didn't
  measure that.

**Nothing in the suite would notice a lost tile today.** A probe field per layer, `hasAllFeaturesInView`, would let
any of these say so. It's the same property as the #2785 fix.

## Recommendation for #2785

1. **Do the small fix:** add `|| !layerView.hasAllFeaturesInView` beside `layerView.updating` in
   `queryPopupLayersAtClick`, still skipping suspended views. It's public, documented for this exact case, and measured
   to agree with the wire 10 of 10. It makes every lost tile clickable on any layer that opens a popup, whatever the
   service. **Suggested priority: Medium.**
   - It's not High because home's move to `Hosted/VTBase3/FeatureServer/0` removes today's cause for buildings.
   - It's not Low because it's the class: any popup layer on any service that fails a query has the same hole. And the
     basemap fails about 3.5% of queries this morning (batch 24).
   - **Its regression test can be cheap:** a unit test with a fake layer view that is settled (`updating: false`) and
     incomplete (`hasAllFeaturesInView: false`) must be asked. On today's code it isn't.
2. **Add `hasAllFeaturesInView` to the map probe's layer report**, so the smoke suite can see a lost tile, and so the
   captures can wait for complete rather than settled, or at least record that they weren't. That's a separate small
   change, worth an issue of its own.
3. **Don't build a retry now.** `refresh()` works but re-asks every tile and blanks the layer, and an interceptor-based
   retry rests on an unproven assumption (section 2). If a service the map depends on keeps failing after the VTBase3
   move, revisit with the open question tested first.

**What this doesn't fix:** with (1) alone, a lost tile is still missing from the drawing. A visitor can click a building
they can't see, and gets its popup. That's better than today, but it isn't a whole fix; only a retry or a reliable
service gives that.
