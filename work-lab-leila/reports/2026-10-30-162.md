## In short: possible, but it needs the maintainer, so I stopped

- **A self-hosted runner can be registered:** the repository has none, and the token on this machine is the maintainer's, with
  repository admin, which is enough to create a repository-level runner.
- **But doing it safely needs settings only the maintainer can change.** This repository is **public**, and seven of its workflows run
  on `pull_request`. For a fork's pull request, GitHub runs the **pull request's own** workflow files, so any contributor could send a
  job to a self-hosted label. Today only first-time contributors need approval. GitHub's own guidance is not to put self-hosted
  runners on public repositories unless that path is closed.
- **That's a security decision, not a YAML change**, so I haven't registered a runner or written the workflow.
- **The design below** is ready to build in an hour once he decides.

**Why that combination matters.** A returning contributor, from a fork, could change `main.yml` in their pull request to
`runs-on: [self-hosted, ...]`. GitHub would run it on the lab machine **without anyone approving it**, with whatever that machine can
reach. A self-hosted runner can be safe on a public repository only once that path is closed.

## What the maintainer would need to decide or grant

**One of these, to close the fork path:**

1. **A runner group limited to `aggiemap-smoke.yml`**, at organisation level. GitHub then refuses that runner to every other workflow,
   including a pull request's edited copy. **Needs an organisation admin** (`admin:org`); it can't be done from here. Limiting a group to selected workflows depends on the organisation's GitHub plan, which I can't see from here either. **This is the
   clean answer.**
2. **Approval for every outside contributor's workflow run** (`approval_policy: all_external_contributors`, a repository setting).
   It's weaker: a maintainer approving a run without reading its workflow diff would still let it in.

**And one of these, for where it runs:**

3. **The runner's machine.** The work machine is where the release tiers are green. **The rule for agents on this machine** is: in a
   container, no host bind mount, no Docker socket, no host network, nothing from `C:\Users`. That rule shapes the design below. If
   the runner is meant to be treated differently, that's his call.

**Or, instead of a self-hosted runner** (options from #2544, plus one):

4. **Option 2: move the nightly into Azure Pipelines**, whose lab agents already exist. No new runner and no public-repository
   exposure, since Azure's agents don't take GitHub pull request workflows. The cost is that results live in two places, and the
   health-issue step would need porting.
5. **A larger GitHub-hosted runner** (more cores) for the production job. It keeps everything in GitHub Actions with no self-hosted

   cores, Esri maps), so more cores should help, but nobody has measured it.

## The design, ready once he decides (option 3 of #2544)

- **Production only, on the lab runner; development stays hosted.** That halves the risk, and production is what #2544 is about.
- **The runner itself** runs ephemeral (`--ephemeral`, one job, then exits), in a container from the same Playwright image the local
  runs use (`mcr.microsoft.com/playwright:v1.64.1-noble`, with the Actions runner added):
  - no bind mounts, no Docker socket, no host network;
  - a fresh container per job, started by a scheduled task on the work machine just before 11:17 UTC;
  - this matches the local runs, which already prove the suite green in that image on this machine.
- **The workflow change:** the production leg of `aggiemap-smoke.yml`'s matrix gets
  `runs-on: [self-hosted, linux, aggiemap-smoke-production]`. It skips `npx playwright install --with-deps`, since the image already
  has the browsers, and keeps every other step, the health-issue step included, so nothing about how results are reported changes.
- **The first night:**
  - **if it's green**, it's comparable to the local release tiers: this week's were 910/3 and 929/2 on dev, and production's
    `map-layers` and `maps` were green on the 28th;
  - **if it's red, honestly red,** it has the same failures a local run would show, which makes it readable.
