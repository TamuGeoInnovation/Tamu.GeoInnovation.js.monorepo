## Task 2: class-validator 0.13.2 → 0.15.1

The lock moves three packages: `class-validator` 0.15.1, `validator` 13.15.15 → 13.15.35 (which clears `validator`'s own
high advisory), and new `@types/validator` 13.15.10. **No code change was needed.**

The breaking changes from the 0.14 and 0.15 changelogs, and what each needed here:

| Change | Where it could bite | Result |
| --- | --- | --- |
| `forbidUnknownValues` defaults to `true` (0.14.0; also when options are undefined, 0.14.2) | A `@Body()` class with no decorators would start answering 400 | **Nothing.** Nest 12.2.0's `ValidationPipe` passes `forbidUnknownValues: false` unless told otherwise (read in this branch's own install), and `gisday-nest`'s global pipe sets nothing. Nothing calls `validate()` directly |
| `@IsIBAN` takes options (0.15.0) | Any `@IsIBAN(...)` | Not used |
| `@IsIn` fails a constraint that is not an array (0.14.1) | Any `@IsIn` | Not used |
| Nested validation errors go to the child (0.14.0) | `@ValidateNested` | Not used |

Only three files import `class-validator`. Two are the GIS Day competitions DTOs (`@IsEnum`, `@IsNotEmpty`,
`@IsOptional`, unchanged), which `gisday-nest` uses. The third is `geoservices/data-api`'s contact DTO.

**The live check.** I built the production `gisday-nest` image from this branch's build output (Node 24.22.1,
`class-validator` 0.15.1 inside) and started it on a throwaway SQL Server restored from `gisday-local.bak`, with Redis.
Every validated POST is behind `JwtGuard`, and guards run before pipes, so an anonymous request answers 401 whatever its
body. So I ran a **throwaway test token issuer on the Docker network**. It generated an RSA key at start, served its JWKS,
and signed one token (audience `gisday.dev.api`, permission `update:competitions`). `AUTH0_ISSUER_URL` pointed at it,
plus the placeholder management settings from batch 12. At 7:02 AM Central, `POST /api/competitions/submissions/validate`:

| Request | Status | Answer |
| --- | --- | --- |
| No token, valid body | 401 | `Unauthorized`: the guard runs first |
| Token, `{"guid":"0000…","status":"verified"}` | **404** | It passed validation and reached the service; there is no such submission |
| Token, `{"status":"approved-by-nobody"}` | **400** | `guid should not be empty`, `status must be one of the following values: unverified, verified, discarded` |

The process stayed up. Everything was removed afterwards: containers, image, database volume, network, key and token.

**Found in passing: `geoservices-nest`'s contact form is not validated.** Its DTO has `@IsEmail()` and `@IsNotEmpty()`, but
`geoservices-nest` registers no `ValidationPipe`, globally or on the route, so the decorators never run. This is the
same before and after the upgrade. Not filed; see the questions below.

## Task 3: swiper 11.2.10 → 14.3.0

The lock moves only `swiper`. **No code change was needed.** 12.0 moved the navigation arrows to SVG, and 14.0 is a
TypeScript rewrite whose notes say it needs no code changes from 12 and has no runtime behaviour changes (13 was
skipped). It raises the browser baseline to Chrome and Edge 110+, Safari 16.4+ and Firefox 110+. The popups use only the
web component (`swiper/element/bundle`) with `slidesPerView`, `speed`, `loop`, `navigation`, `preventClicks` and an
`init` handler. Nothing else uses Swiper: UES reaches `PoiPopupComponent` through its map definitions.

**The images** (`docs/screenshots/2111-swiper-14/`). Before is `development` on the AggieMap dev server with 11.2.10;
after is the branch with 14.3.0, from the same worktree, framed by the same scripted steps. Desktop is 1440 × 900. Phone is
390 × 844 at 2×, with the popup's bottom sheet pulled up, because it opens collapsed and hides the carousel otherwise.

**What looks different: only the arrows.**

- **Pixel diff, before against after.** The two portal popups are identical, 0 pixels. The carousels differ only in a
  32 to 65 px tall strip across the photo where the arrows sit: 167 and 171 pixels on desktop, 534 and 638 on the phone.
- **The button sizes.** Swiper 14's navigation buttons are 33 × 33 px; 11's were 20 × 33. The arrow is centred in a
  wider button, so it sits a few pixels further in from the photo's edge. Our `swiper-container
  .swiper-button-prev/next` rule in `libs/sass/components/_popup.scss` was meant to size them, but the buttons are in the
  component's shadow DOM, so it applies on neither version. The 20 px came from Swiper 11's own styles.
- **Behaviour.** On both versions every popup initialises, opens on its first photo, and the next arrow moves it to the
  second. I did not test looping past the last photo or opening a photo full size. The release-notes row asks testers
  to check both on dev.
