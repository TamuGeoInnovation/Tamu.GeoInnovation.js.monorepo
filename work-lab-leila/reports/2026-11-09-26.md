## 1. The change

In `libs/maps/esri/src/lib/services/map/click-query.ts`:

```ts
return layerView ? !layerView.suspended && (layerView.updating || isMissingFeatures(view, layerView)) : layer.visible;
```

with

```ts
function isMissingFeatures(view: esri.MapView | esri.SceneView, layerView: esri.LayerView): boolean {
  return view.type === '2d' && (layerView as esri.FeatureLayerView).hasAllFeaturesInView === false;
}
```

- **Only `=== false` counts.** A layer view without the property isn't taken to be missing anything. That covers a
  graphics layer's view, and the test stubs, which had no such property, so a bare `!hasAllFeaturesInView` would have
  read `undefined` as incomplete.
- **2D only, and why:** the property exists in 3D, but means something weaker.
  - `FeatureLikeLayerViewBase3D` reads it from its graphics pipeline, which returns `false` whenever its controller
    lacks the property.
  - `FeatureTileController3D` computes it from `_tileFetcher.showsAllFeatures`, which is also false when the scene thins
    a layer's features for its level of detail.
  - So in a scene, `false` doesn't mean "a query failed", and honouring it would make every click ask every layer. I
    measured only 2D, and the doc comment says why 3D is left out.
- **The same layer filter applies:** only layers with a `popupComponent` and a `queryFeatures` are asked.
- **The doc comment** now says drawn isn't complete, why, and what it costs.

## 4. A correction to batch 25: on the main map, a lost tile costs clicks, not pixels

**The buildings you see on the main map are the basemap's, not the buildings layer's.**
- I captured three loads with nothing forced. Each lost a **different, real** buildings tile, recorded on the wire.
- The three images are **pixel-for-pixel identical** in the map area: 0 differing pixels in 915×770.
- So `buildings-layer` (`main.definitions.ts`, `essential`, `listMode: 'hide'`, no renderer of its own) adds nothing
  visible over the basemap's vector tiles there. It's the layer that answers clicks.

**What this means:**
- **On the main map, this fix is the whole visible fix.** A lost buildings tile was an unclickable square, and now it
  isn't.
- Batch 25's "13 and 33 buildings missing" was the layer view's count, which is true, but they weren't missing from the
  screen. I should have checked pixels before writing "missing from the drawing".
- **On a map whose popup layer is also what draws** (an event map's lots, say), a lost tile is still missing from the
  picture. This fix makes the gap clickable, not drawn.

## 5. The cost, measured

**The property the first fix protected holds.** With the fix, on a complete map, a click on bare ground sends **0**
buildings queries.
- Five control loads with nothing forced, each recording every real tile answer.
- In the 3 loads where the buildings layer received every tile, it read `hasAllFeaturesInView: true` and the click sent
  0.
- In the other 2, the **real** service had lost a buildings tile (layer 1), and the click sent 1.
- A lost tile on layer 2, a different layer, left the buildings layer complete (control 2).

**On a map with one incomplete layer:**
- **Each click whose hit test finds nothing asks that one layer once:** one small point query, about 300 ms by batch
  24's numbers. A click on a building elsewhere on that map, found by the hit test, asks nothing (that path is
  unchanged).
- It lasts the whole visit, since nothing makes the layer complete again.
- **No other layer is asked.** On the main map only buildings is visible and has a popup at load, so it's one query a
  click at most.

**Is it worth bounding? I'd say no.**
- It's the same cost the first fix accepted for every click while a map draws, and it applies only after a failure.
- A bound, such as "stop after N clicks", would bring back exactly the unclickable square it exists to remove.
- **If a service started failing on most loads, the cost would be one query per bare-ground click**, which is still
  small. And it's what `hasAllFeaturesInView` is for.

**How often it applies today:**
- The main map's buildings layer is layer 1 alone. Batch 24 measured 41 of its 960 queries failing (4.27%), so at 12
  tiles a load, **about 4 loads in 10** lose one.
- That matches this batch's controls, where 2 of 5, then 3 of 3, lost a real buildings tile.
- **The release-notes entry says "about a third", which is a little low.** Change it to "about four in ten" if you
  prefer; I didn't rewrite the branch for it.
- Home's move of buildings to `Hosted/VTBase3/FeatureServer/0` should take it close to zero.
