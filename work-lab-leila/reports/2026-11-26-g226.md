## #3708: the two tools

On `work-mailbox`, beside `roster.sh` and `queued.sh`. Commits `53c6afa54`, then a one-line fix to a cell's text.

- **`tools/machine-health.sh <machine>`** measures one machine and writes `<machine>/HEALTH.json`. It takes about 50
  seconds here and commits nothing.
  - **What it measures:** everything in the issue's body, and the eleven measures in its comment.
  - **What it can't:** it writes `"not measured here"` for any measure it can't take, and `health.sh` shows that grey.
- **`tools/health.sh`** reads every `*/HEALTH.json` on `origin/work-mailbox` into one Markdown table, one row per
  machine. Each value is green, amber or red, and the row takes its worst colour. Grey never outranks a real colour.
- **The thresholds are read, not copied.**
  - **Where from:** `CHECK_SWEEP_FREE_GB` and `CHECK_MIN_FREE_GB` come from `origin/development:scripts/check-in-volume.sh`,
    and `TIDY_IMAGE_MAX_GB` from `scripts/tidy.sh`, with an environment variable of the same name still winning.
  - **If one is missing:** it stays unknown and that measure goes grey. No fallback number is written anywhere.
  - **Proved by a test:** a fixture script whose default is 70 instead of 60 turns 65 GiB amber.
- **No jq:** none of these machines has `jq`, and `python` here is only the Windows Store stub. So the JSON is flat,
  one `"key": value` per line, written and read with `sed`.
- **No secrets:**
  - **The Auth0 settings file:** reported as present or absent, never opened. A test puts a fake secret in a fixture
    file and checks no byte of it reaches the output.
  - **The SSH greeting:** it names a GitHub login, so only `ok` or `failed` is kept from it.
  - **The build agents:** their containers are only counted by name.
- **`gh` is here:** the batch says this machine has no `gh`, but it has one (2.102.0), so the GitHub measures are
  filled in.

**Tests, written first.**
- **Before the tools existed:** `tools/health.test.sh` stopped at `read_thresholds: command not found`, and
  `tools/machine-health.test.sh` gave 1 passed, 21 failed.
- **Now:** **43 of 43** and **22 of 22**. They cover:
  - every rule at and either side of its line;
  - grey for what isn't measured;
  - worst-wins, including red over grey;
  - the threshold-moves case;
  - a two-machine table, one green and one red;
  - JSON escaping;
  - the SSH greeting and the gh scope;
  - orphan detection;
  - the secret case.

**Two places I narrowed or adjusted a measure:**
- **Stale Nx records:** I count checkouts holding an Nx task database (`.nx/workspace-data/machine-v*.db`, what #1626
  waits on) while no Nx runs. I don't count every `.nx/workspace-data`, whose file maps and hashes are ordinary cache. I
  can't read the database's rows without SQLite, so this counts where a stale record *can* be, not where one *is*.
- **When `origin` was last fetched:** read before the script's own fetch, or it would always say "now".

## Questions

**Q-g226-1: should GitHub access over SSH be red on a machine that pushes over HTTPS?** The rule from #3708 is
"`ssh -T git@github.com` ... any failing: red", from #3273, where an expired key and WSL's `bash` looked identical.
This machine has never used SSH for GitHub. Its remotes are HTTPS, and pushes go through `gh`'s credential.
- **(a)** Treat GitHub access as ok when the machine's own push route works: SSH where the remotes are SSH, `gh` where
  they are HTTPS.
- **(b)** Keep SSH required everywhere, and set up a key here.

I recommend (a). It measures what the machine actually depends on.

**Q-g226-2: the lab's build agents are not on this machine.** The measure is red. There is no `tamu-build-agent-lab-*`
container at all, running or stopped, and no Azure Pipelines service. They may have moved to another machine or been
removed, which I can't tell from here. If they belong here, someone should know builds aren't being picked up by them.
If they moved, the "lab only" rule should name the machine they're on. I recommend asking the maintainer which.
