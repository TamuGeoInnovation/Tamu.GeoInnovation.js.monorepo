### Finding: which layer refuses the oversized logo

**What the first run showed:**
- nginx's log has `client intended to send too large body: 6291977 bytes` and answered **413 itself** (585-byte HTML);
- the API never saw that request;
- `gisday-local-static.conf` sets no `client_max_body_size`, so nginx's 1 MB default applies. Nothing in this repository sets one.

**What the rerun with the limit raised showed:** I put `client_max_body_size 16m` in my copy of the config, for this batch only, and ran
part 1 again:
- every line PASS again;
- this time nginx passed the body through, and **the API answered 413** (73-byte JSON), at its own 5 MiB limit
  (`DEFAULT_UPLOAD_LIMITS`).

**So:**
- **The API's refusal works**, and the release line passes either way.
- **Locally, though, the line has been testing nginx's default.** And **no upload over 1 MB can succeed through `web --static`.** The
  speaker photo below was refused by nginx the same way (`POST speakers 413`, HTML body) until the limit was raised.
- **Production's limit is set in the cluster's configuration**, not here, so this says nothing about production.

**Finding on #2426: the file name and the bytes disagree.**
- The stored file is named `<speaker>-photo-1900.png` and holds **JPEG data** (`FF D8`): the resize re-encodes a PNG as JPEG and keeps
  the name.
- nginx picks a content type by extension, so it would serve these JPEG bytes as `image/png`. Browsers sniff image types, so it
  displays. I didn't capture the header before the stack was removed.
- It's harmless, but worth knowing before anyone writes a check on file extensions. A question for the director, not a fault.
