## What this changes

`viewEvent` (#3493) kept the `view.on` handle in one variable in its closure. `fromEventPattern` calls `add` once per
subscriber, so a second subscriber to the same observable overwrote the first one's handle. Whichever unsubscribed
first then took the **other's** handler off the view and left its own registered for good.

- **One handle per subscription.** `add` now returns the handle, and `remove` takes the one `fromEventPattern` hands
  back to it, guarded with `handle?.remove()` for a handle that never arrived. This is the shape `watchAsObservable`
  has (#3592).
- **The comment** beside it says the handle is per subscription, and why. `watchAsObservable`'s comment says the same,
  so the two read alike.
- **Not reached today.** All five call sites create their `viewEvent` inside a `switchMap`, which subscribes to each one
  once:
  - the trip planner's top bar;
  - the viewfinder, twice;
  - the click coordinates;
  - the trip planner service, through `viewEventFromStore`.

  So this fixes a latent fault before it reached anyone, and nothing a visitor sees changes.
- **`arcgisSignal` is untouched.** It keeps its handle inside each run of its effect, so it never had this fault.
