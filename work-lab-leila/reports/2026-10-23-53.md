### One deliberate change from Microsoft's script: the job cannot read the token

Microsoft's sample runs as the agent's user and writes the token to `/azp/.token`, a file that user can read. **The job runs as the same user, so
fork code could read the PAT.** It could also read `/proc/1/environ`, which keeps the token after `unset`. With a pool-management token, that code
could register its own agent in `Linux-Build` and receive other pull requests' jobs.

So **`start.sh` starts as root and keeps the token only in its own shell's memory**. It runs `config.sh`, `run.sh` and `config.sh remove` as `agent`
(`setpriv`). The token reaches `config.sh` through `VSTS_AGENT_INPUT_TOKEN`, set on that one command only, so it is never on a command line. The
container keeps only `SETUID`, `SETGID` and `KILL` (to switch user and stop the agent), with `no-new-privileges` set; `agent` has no capabilities.
**If the root entrypoint is not acceptable, say so.** Microsoft's layout is a two-line change back, with the exposure above.

## 2. The token never reaches the job: a stub test

The real agent needs Azure, so I used a test image built on top of this one. Its `config.sh` and `remove` only report whether a token reached
them, and its `run.sh` stands in for the job and looks for the token. A copy of `sleep` named `Agent.Listener` stands in for the listener. It was

| | Normal end | Stopped mid-job (`docker stop`) |
| --- | --- | --- |
| `config.sh` ran as | `agent`, token given | `agent`, token given |
| The job: token in its environment | **0** | **0** |
| The job: `/proc/*/environ` it can read holding the token | **0** | **0** |
| The job: `/proc/1/environ` | **refused** | **refused** |
| `config.sh remove` | ran, token given | **ran**, token given; the listener ended with 130 |
| Container exit | 0 | 143, at once |

**A bug found and fixed:** the first stop test did not remove the agent. The agent's `run.sh` runs `Agent.Listener` in the foreground, so a signal
to `run.sh` waits for the job to end, and `docker stop` killed the container first. `start.sh` now signals `Agent.Listener` itself (`pkill -INT
-x Agent.Listener`). Microsoft's sample has the same gap.

## Residual risk: the network

**Fork code on the agent can reach the network, the lab's local network included.** The container is on Docker's bridge and can reach whatever the
host can. Before the pool takes fork pull requests unattended, **restrict its egress**. One way is a Docker network whose host firewall rules
allow the internet (npm, GitHub, Azure) and drop the private ranges (10/8, 172.16/12, 192.168/16) and the host itself. On Windows with Docker
Desktop the rules have to sit inside its VM, so this needs a small design of its own. I recommend it as its own batch.

   `templates/jobs/build.yml` downloads the secure file `app_configs.zip`. Turning off *Make secrets available to builds of forks* (which is

   `setup-organization.ps1` with `-DryRun` only, and to change only the comment setting by hand. I told the maintainer the same when they asked
