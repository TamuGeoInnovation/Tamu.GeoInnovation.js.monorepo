## 3. The port: every call site, before and after

Nothing outside `ManagementService` calls the Auth0 client. Its callers keep its methods, unchanged: the GIS Day user pages and profiles
(`user-info.provider`), rosters (`class.provider`), leaderboards and submissions.

| Where | auth0 3 | auth0 7 | Response |
| --- | --- | --- | --- |
| `getUserMetadata` | `client.getUser({ id: userId })` | **`client.users.get(userId)`** | resolves to the user itself: no `.data` |
| `updateUserMetadata`, first read | `client.getUser({ id: userId })` | **`client.users.get(userId)`** | the same |
| `updateUserMetadata`, the write | `client.updateUser({ id: userId }, payload)` | **`client.users.update(userId, payload)`** | the updated user itself |
| `getUsers` | `client.getUsers({ sort: 'name:1' })` | **`client.users.list({ sort: 'name:1' })`** | a **`Page`**: the users are **`.data`**; `hasNextPage()`/`getNextPage()` and `for await` reach further pages |
| constructor | `new ManagementClient({ domain, clientId, clientSecret })` | the same | 7 still takes client credentials and gets its own token |

**Pagination:** 7's `list` sends the API's own defaults, `page=0&per_page=50&include_totals=true`, and reads the envelope (`users`). 3.x sent
no page and got the same first 50. **So `getUsers` returns the same first page of up to 50 users as today.** That is a limit worth knowing
(question 1).

**Types:** 4 and later stopped exporting `User`, `AppMetadata` and `UserMetadata`. The service now exports them:
- `User` is 7's `Management.UserResponseSchema`;
- the two metadata types keep **3.x's shape, any value under any key**. 7 types metadata `Record<string, unknown>`, and the build showed what
  that does: `class.provider.ts:176` reads a roster entry's `user_metadata.education.id`, and every such read would need a cast.
- `user-info.provider` now imports them from `@tamu-gisc/common/nest/auth` instead of from `auth0`.

**Errors:** 7 throws its `ManagementError` where 3 threw its own error. The service's handling only reads `err.message`, so a missing user
still answers 500 from `getUserMetadata`, as before.

## 4. Proof without a tenant

**A new spec, `management.service.requests.spec.ts`, with 9 tests.** `fetch`, which 7 uses for every request, is replaced in the test by a
stand-in for the tenant: it answers `POST /oauth/token` and `/api/v2/users…` as the API does, including the `include_totals` envelope, and
records each request.

| Test | Checks |
| --- | --- |
| token | a `client_credentials` `POST /oauth/token` with the client id and secret; every API request carries `Bearer <that token>` |
| `getUserMetadata` | `GET /api/v2/users/auth0\|1`; the answer mapped to the profile with only the filtered metadata; a missing user answers 500 |
| `updateUserMetadata` | `GET` then **`PATCH /api/v2/users/auth0\|1`** with exactly the filtered `app_metadata`/`user_metadata`, the composed `name`, and **no email**; a social user's name and email left out; the updated user mapped |
| `getUsers` | **`GET /api/v2/users?sort=name:1&page=0&per_page=50&include_totals=true`**, one request; each user mapped, with `connection` and `social` |
