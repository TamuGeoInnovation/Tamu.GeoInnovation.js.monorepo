- **The lock against `development`: only their tree.** 15 keys are added:
  - `@jimp/core`, `file-ops`, `js-jpeg`, `js-png`, `plugin-resize`, `types`, `utils`;
  - jimp's nested `file-type` 21.3.4, `mime` 3.0.0 and two `zod` 3.25.76;

  `pngjs` (already locked, `dev`) becomes a production dependency. **Nothing else moves.** The newest of these is `@jimp/*` 1.6.1 (7 April);
  every one is past 7 days.
- **No install scripts:** `install-scripts.mjs` still reports *11 of 11 allowed*. A clean `npm ci` under the allowlist passed (*added 1907
  packages*), and *1906 packages have verified registry signatures*.
- **No WebP:** jimp has no WebP codec in these packages. A WebP photo (production has one, 0.52 MB at 768 × 768) is kept as it is. Its shorter
  side is within the target anyway.
- **It is slow, but it runs rarely:** pure JavaScript decodes, resizes and encodes a 12 MP photo in about **1.1 s** on a quiet machine (3000 px:
  0.9 s; 1200 px: 0.25 s). That blocks the API's event loop for that long, once per photo upload, an admin action. It is acceptable for
  speakers; I would not use it on a busy public route.

## The size and quality chosen

- **The shorter side is scaled down to 840 px.** That is twice the largest place a photo is drawn, for sharp screens. I measured on the local
  stack at 2560, 1920, 767 and 700 px wide:

  | Where | Drawn at |
  | --- | --- |
  | a presenter's own page, at tablet widths (767 px and below) | 420 × 322 |
  | a presenter's own page, on a desktop | 360 × 345 |
  | a Presenters card | 253 × 255 |

  Photos use `object-fit: cover`, so a shorter side of 840 covers all of these. The aspect ratio is kept, so a portrait photo becomes
  840 × 1120.
- **JPEG at quality 80; PNG losslessly, at deflate level 9,** without the alpha channel when every pixel is opaque.
- **EXIF is removed** (and XMP, and PNG text chunks), after the EXIF orientation is applied.
- **Photos left alone:** a photo within 840, with no metadata and under 300 KB, is left exactly as it was. Re-encoding a photo within the size
  only happens if it saves at least a tenth.
- **One setting for both:** `SPEAKER_PHOTO_FIT` in `libs/gisday/platform/data-api/src/lib/speaker/speaker-photo.ts`, used by the upload and the
  script. The measurements are written beside it.
- **Where the code lives:** the resizing is a new shared library, **`@tamu-gisc/common/node/images`** (`libs/common/node/images`, beside
  `common/node/fs`), exported for the next caller. Sponsor logos are stored the same way and could use it.

## The script for the photos already stored

**`nx run gisday-nest:fit-speaker-photos [--dir=<folder>] [--apply] [--backup=<folder>]`** lives at
`apps/gisday-nest/src/scripts/fit-speaker-photos.ts`, beside the migration targets, and runs the same way (ts-node).
- **What it works on:** the uploads' `images/speakers` under `APP_DATA`, by default. It writes in place under the same names, so no database row
  changes.
- **Dry run by default.** `--apply` first copies every photo it will change to `<dir>-originals`, and never replaces a copy already there. Only
  then does it write.

**Proved on a scratch copy of local uploads.** The seed has no speaker photos (all placeholders), so I gave eight participating speakers real
photos already in this repository: the five Sidewalk competition photos, `landing-bg.jpg`, and two large PNGs. I did this in the throwaway
`lab142` database and a scratch uploads folder, mounted into the site at `assets/uploads`, as production's nginx serves the volume.

```

CHANGE  …-IMG-1415.JPG     1140 x 1520, 506 KB  ->  840 x 1120, 402 KB  (scaled to 840 x 1120)
```

**The second run found two photos to re-encode for a few bytes each.** Repeated runs would have cost JPEG quality every time, so I fixed it
(`11281529b`) before this final run, and added a spec for it.

## The page weight: before and after

`presenters-weight.cjs` (Playwright, 1440 × 900) measures the speaker photos on the local Presenters page, the same way both times:

| | Speaker photos | Total |
| --- | --- | --- |
| **before** (as uploaded) | 506, 436, 440, 485, 563, 477, 463, 2939 KB | **6.16 MB** |
| **after** `fit-speaker-photos --apply` | 402, 310, 361, 1480, 432, 446, 563, 394 KB | **4.29 MB (−30%)** |

The page looks the same; both screenshots are in `docs/screenshots/2352-gisday-speaker-photo-size/`. **These photos were already close to the
target size** (1140 × 1520), so this understates the effect. Production's large photos are over 1 MB at camera resolution: a 3000 px JPEG of
8.9 MB fell to 84 KB in the timing run. **PNGs stay large**, because PNG is lossless and the name, and so the format, must stay: the 2.9 MB PNG
only halved, to 1.5 MB.
