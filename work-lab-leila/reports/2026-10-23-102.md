## 1. Is it reachable? No

**The advisory** (GHSA-xcx6-jx8p-x3h5, published 23 Oct, 5:16 PM Central) is an origin validation error in **MSAL Node's `auth_code` flow**. Its
workaround is to pass only the code to `acquireTokenByCode`. Affected: `>= 5.0.0-beta.0, < 7.1.0`.

**The only path in** (`npm ls`): `mssql` 12.7.11 → `tedious` 20.3.8 → `@azure/identity` 4.14.0 → `@azure/msal-node` 6.0.1. **No code of ours
imports any `@azure/` package.**

**How tedious uses `@azure/identity`.** `connection.js` requires it at load, so it is always in memory, but it **builds a credential only for an
Azure AD authentication type**:

| tedious `authentication.type` | Credential | MSAL call |
| --- | --- | --- |
| `default` (SQL login), `ntlm`, `azure-active-directory-access-token` | none | none |
| `azure-active-directory-password` | `UsernamePasswordCredential` | `getTokenByUsernamePassword` |
| `azure-active-directory-service-principal-secret` | `ClientSecretCredential` | `getTokenByClientSecret` |
| `azure-active-directory-msi-vm`, `-msi-app-service` | `ManagedIdentityCredential` | managed identity, no code flow |
| `azure-active-directory-default` | `DefaultAzureCredential` | see below |
| `token-credential` | whatever object the caller passes | the caller's |

- **Where the code flow is in `@azure/identity`.** The only MSAL code-flow and interactive calls are in `msal/nodeFlows/msalClient.js`. They are
  called only by `AuthorizationCodeCredential`, `InteractiveBrowserCredential` and `VisualStudioCodeCredential`. **tedious never builds the first
  two.**
- **`DefaultAzureCredential`'s chain:** environment, workload identity, managed identity, Azure CLI, PowerShell, azd, VS Code and the broker. Its
  only interactive members need plugin packages: VS Code throws `CredentialUnavailableError` without `hasVSCodePlugin()`, and the broker needs
  `@azure/identity-broker`. **Neither plugin is installed** (`node_modules/@azure` has no `identity-vscode` or `identity-broker`).

**How our APIs configure `mssql`.** No values were printed.
- `gisday-nest` and `mailroom-nest` (`environment*.ts`) pass `username` and `password` from `TYPEORM_USERNAME`/`TYPEORM_PASSWORD`, and `extra`
  from `JSON.parse(TYPEORM_EXTRA)`.
- TypeORM's `SqlServerDriver` passes `authentication: credentials.authentication`, which is unset, so mssql sets tedious's type to
  **`default`, a SQL login**.
- No file in the repository sets an `authentication` type. The samples' `TYPEORM_EXTRA` holds only `trustServerCertificate`.

**What I cannot see:** the deployed `TYPEORM_EXTRA` values, which live outside the repository. **It would not matter.** `extra` could carry an
`authentication` object, but every type it could name is in the table above, and none runs the code flow. The one open-ended type,
`token-credential`, needs a live object with a `getToken` function, which JSON cannot carry.

**So no code path here calls `acquireTokenByCode`.**
