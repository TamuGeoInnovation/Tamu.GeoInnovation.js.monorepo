## 2. The fix

- **One shared timeout**, `libs/common/nest/services/src/lib/mailroom-timeout.ts`, exported from the shared services (beside
  `upload-limits`) and **read by all three calls**:
  - **`MAILROOM_TIMEOUT_MS = 10_000`: 10 seconds.** A mail through mailroom normally takes well under a second. The largest request, the helper
    forwarding a message with its attachments (up to 50 MiB), crosses the internal network in a few. So 10 s leaves room for a slow moment,
    while a mailroom that never answers costs a visitor 10 s, not a hung request.
  - **The `MAILROOM_TIMEOUT_MS` setting overrides it** (the tests use 300 ms; an environment that needs longer can set it).
  - `mailroomRequestOptions()` gives got `timeout: { request }`; `isMailroomTimeout()` recognises got's `TimeoutError` (`ETIMEDOUT`).
  - **No retry:** got never retries a POST, so a timed-out mail is not sent twice. The tests check one request each.
- **A timeout answers 504** (`GatewayTimeoutException`) in all three; other failures keep their existing 500.
- **The helper** reads every answer itself (`throwHttpErrors: false`), so a mailroom 4xx/5xx reaches its own check and becomes **the
  `HttpException` it always meant to throw**, with mailroom's `exception` as the reason. An error page that is not JSON becomes "Mailroom
  answered <status> with no readable reason." instead of a `JSON.parse` failure. A 2xx with no exception still answers 200, unchanged.
