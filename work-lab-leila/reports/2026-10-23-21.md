`geoservices-nest` builds because it uses none of `auth0`, `openid-client` or `@types/got`. So this is Nx's lock pruning, not the
APIs' code. It is the same for all three, since `mailroom-nest` and `mailroom-helper-nest` use `openid-client` too.

## 9. Not pushed

The check passes, but step 4 does not, for three of four images. **What is left:** the generated locks have to install. Options,
yours to choose; I have tried none:

(a) keep `generatePackageJson` but have the image run `npm install --omit=dev` instead of `npm ci`. That installs from the
generated `package.json` and repairs the lock. It is less reproducible, since versions can float within ranges.

(b) Nx's `"generateLockfile": false`, so only `package.json` is generated, and the image runs `npm install`. That has the same
trade-off as (a).

(c) keep the root lock and prune differently, for example `npm ci --omit=dev` from the root files, then `npm prune` to the
generated `package.json`.

(d) report the pruning bug to Nx. The nested entries above are a small reproduction.

**And, separately, for the three accepted findings:** they live in the base image's npm. Removing npm from the runtime stage
(`RUN rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx` in the `node:24.22.1-alpine` stage, which
runs `node main.js` and never needs npm) would remove all four from every API image, whatever is decided about the rest.
