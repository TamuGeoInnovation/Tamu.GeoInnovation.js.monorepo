**The cause, from the probe's `renderers()` and the service:**

| Layer | `symbology` | The renderer the map draws with | The republished service |
| --- | --- | --- | --- |
| `baseball-event-lots` | `portal` | `uniqueValue` on **`baseball`**: `AnyValid`, `Permit`, `SeasonPass`; no default symbol | fields `event`, `type`, `name`, `category_type`; **no `baseball`**. `where=baseball IN (...)` answers *Field name 'baseball' does not exist* |
| `baseball-gate-road-closure` | `portal` | `uniqueValue` on `baseball`: `1` | no `baseball`. Its tile query also fails: `JSONObject["objectid_1"] not found` |
| `baseball-event-symbols` / `-accessible-symbols` | `portal` | `uniqueValue` on `type,event` (`$10 Bus Parking,Baseball` ...) | layer 0 has `name` and `category_type` only, and no `event` |
| `baseball-accessible-shuttles` | `portal` | `simple` | draws |

- **The service's own `drawingInfo` is `simple`** on every layer, so the app falls back to the portal item's renderer, which still
  describes the old schema.
- **On dev** the same layers report `symbology: service`, with `uniqueValue` on `type` or `name`, fields that exist, so they draw.
- **The fix is the maintainer's call:** either the portal items are republished with the new schema's symbology, or the definition
  overrides it with a reason, as `docs/map-layers.md` says.

**Why the suite missed it:** the baseball map is behind a builder, so `map-layers.spec.ts` skips it. That's #2467. Its *drawn* check
would ask the renderer for a symbol and get none. I haven't run `test/2467-builder-map-layers` against production: its inventory is
dev's, so on production those maps are still skipped.
