## What it checks

A new `describe` in `services.spec.ts`, **GIS layers hand over every feature they hold**, with one test per service in
`connections.ts`, beside the existing GIS-service tests and skipped by the same rules (retired, `ALLOWED`).

1. **Layers, not roots.** A URL ending `/MapServer/<n>` or `/FeatureServer/<n>` is checked as it is. A
   `MapServer` or `FeatureServer` root is asked for its `layers` (`?f=json`), and every feature layer under it is
   checked (group layers are left out because their sublayers are listed too). So the layers the definitions add
   an index to, such as `${tsMainUrl}/6`, are covered through the root.
2. For each layer: `returnCountOnly` for the total, `maxRecordCount` from the metadata.
3. **Total at or below the cap: passes.** Above it: one record is asked for at `resultOffset=<maxRecordCount>`,
   `resultRecordCount=1`. **A refusal fails, with the service's own message, and so does an empty answer.**
4. Every layer's numbers go into the test's annotations and the log (`HOLDINGS <service> <layer>: <total> of
   maxRecordCount <cap>, <result>`), so a passing run still shows what is near the boundary.

The judging is a pure function, `completenessProblem()`, so it can be tested without a service. The fetching is in
`holdingsOf()`; a layer that is not a feature layer (a table), or whose count fails, is noted as **not checked**
rather than failed, because counting is the existing checks' job.

### One thing the query has to get right

**The past-the-cap request is ordered by the layer's `objectIdField` when its metadata names one, and otherwise
not ordered at all.** My first version guessed `OBJECTID` when it was missing, and four layers failed on it:
Accessible Building Entrances and the basemap's 20, 63 and 64, all "Invalid or missing input parameters." **That was
the question's fault, not the layers'.** Map service layers (`MapServer`) do not give an `objectIdField`. Basemap 20's
OID field is `OBJECTID_12`, and Accessible Building Entrances' only OID field is its attachments' `ATTACHMENTID`, which
is refused too. Asked without an order, all four page correctly. A comment in the code says this.

- `TS_Events/MotorcycleParking/MapServer/0` (44,980 of 2,000): **"Pagination request requires either orderBy field

**So about one paged request in ten is refused, on both `gis.tamu.edu` and `arc.ts.tamu.edu`, and the same
question gets a different answer on the next try.** Ordering does not prevent it; it only changes the message. That
looks like one or more machines behind each address that cannot page, the same thing as #2080's "fails about half its
queries" but less often. For a map it means **a layer over its cap sometimes draws short with no error shown**, which
is exactly what #2101 is about, and it is not limited to Accessible Building Entrances.
