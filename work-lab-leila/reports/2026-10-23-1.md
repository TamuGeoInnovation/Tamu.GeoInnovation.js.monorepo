### `gisday-nest` running

I started the image against a throwaway SQL Server, made by `scripts/gisday-local.sh db` and `restore` from `apps/gisday-nest/src/database/gisday-local.bak`, with a scratch settings folder and generated passwords, plus Redis. Its settings were `apps/gisday-nest/local.env.sample`.

- **`GET /api/seasons/active`: 200**, the 2026 season.
- **One thing differs from the batch's wording: the sample alone does not start the production image.** It exits at startup with `Error: Management service configuration is missing required parameters.` The sample's own comment says why: only the local build reads `AUTH0_MANAGEMENT_DISABLED`, and the production configuration requires all three `AUTH0_MANAGEMENT_*` values. I passed obvious placeholders (`AUTH0_MANAGEMENT_DOMAIN=placeholder.invalid`, `..._CLIENT=placeholder`, `..._SECRET=placeholder`), which the constructor accepts without any network call, and it started. This is how the production image is built, not something the Node move changed.

### Malformed Brotli

At 6:13:25 AM Central I sent `POST /api/seasons` with `Content-Type: application/json`, `Content-Encoding: br` and 512 random bytes as the body. That is malformed Brotli, not an exploit.

| Body | Status | Answer |
| --- | --- | --- |
| 512 random bytes | **400** | `{"statusCode":400,"message":"Decompression failed"}` |
| Control: `{"year":2099}`, properly Brotli-compressed | 401 | `Unauthorized`. The body was decoded and the request reached the auth guard |

**The process stayed up**: still running, 0 restarts, and `GET /api/seasons/active` answered 200 again afterwards. The log shows body-parser's 400, and nothing else.

The four images, both containers, Redis, the database volume, the network, the scratch settings folder, the `node_modules` volume and the worktree have all been removed. No branch was pushed and nothing was opened.
