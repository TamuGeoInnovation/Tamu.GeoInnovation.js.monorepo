## 3. Nothing changed at run time

**`gisday-nest` builds in production configuration** at both PR 3560's tip `76c2a50d8` and on this branch: `exit 0`
each time, in the check volume's clone.

**TypeORM's metadata** (`getMetadataArgsStorage()`):
- **How:** each production bundle was loaded far enough for its entity decorators to run, with the bootstrap's
  `process.exit` held back, and its columns, relations and tables were written out, one sorted line each. That's 241
  columns, 95 relations and 54 tables on both sides.
- **Without explicit types:** 26 columns read `type=fn:Object` where they had read `fn:String`. TypeORM can't map
  `Object`, so the API would have created or compared those columns wrongly.
  - **Where:** `events` (6), `speaker_edits` (6), `speakers` (4), `submissions` (4), `speaker_email_sends` (3),
    `assessments`, `rubrics`, `speaker_edit_links` (1 each). All are in the platform API's `all.entity.ts`; PR 3560
    had already covered the competitions tables.
- **The fix:** each now says `type: 'nvarchar'`. That's what SQL Server's driver makes of `String` (`normalizeType`
  returns `"nvarchar"`), and both get the same default length of 255 (`getColumnLength`). A note at the top of the
  entity file explains this for the next one.
- **After:** the two dumps are **identical** once `String` is read as `'nvarchar'`. The only raw differences are those
  26 lines, and no column reads `Object`.

**Every other decorator type:**
- **How:** both sides compiled with `tsc` to unminified JavaScript (282 files each), and each `__metadata(…)` call diffed
  by class and member: 873 decorated members on each side.
- **Entity properties:** 71 `design:type` entries change, every one in an entity file. TypeORM ignores them where a
  column names its type or a relation names its target, and the comparison above shows nothing else reaches it.
  Nothing in GIS Day's API reads `design:type` (`enableImplicitConversion`, `plainToInstance`: none).
- **Three route handlers' parameter types** become `Object`:
  - `SpeakerController.markBadgesPrinted` and `clearBadgesPrinted`, which were `Array`;
  - `UserSubmissionController.deleteEntities`, whose body `guid` was `String`.

  **Why that's harmless:** Nest's `ValidationPipe` skips `String`, `Array` and `Object` alike (`toValidate`, its
  `types` list), and the app's pipe is `{ forbidUnknownValues: true, whitelist: true }`, with no transform. So those
  requests are treated as before.
- **Constructor parameters:** none changed, so dependency injection is unchanged.

- **None in the app's own files.**
- **By code:** TS2345 232, TS2322 90, TS18048 87, TS18047 35, TS2532 29.

**The baseline:** three library configurations already fail without the flag (20, 28 and 2 errors), and their "with it"
counts include those. That's the library configurations' own gap, not `strictNullChecks`.

**What it suggests for the next step:** the app itself is clean, and most errors are in shared code. Turning the flag on
in `gisday-angular` waits on the shared libraries. The GIS Day libraries could each go on in their own configuration
first, as the API libraries did, starting with `platform/ngx/data-access` (1 error) and `competitions/ngx/data-access`
(6).
