## 1. The reproduction: which part was wrong

**The stack** was a throwaway `lab180`, as in batch 178:

- API `gisday-nest:sha-d834cc8`, the newest GIS Day API;

**The seed has no VGI form for 2026**, so the Designer showed only "Fetch Schema". **In the throwaway database only**, I copied 2025's
form and attached the copy to the 2026 season.

**The Designer's two fields are `datetime-local` boxes** with `step` 300. Its picker uses the `datetime-local` path, so **today's
`MatTimepicker` list isn't involved**; that is used only for a time alone, the event times. I typed into "Submissions stop counting
at" part by part, as a person does, recording every `change` event:

| What I did | `change` events | Result |
| --- | --- | --- |
| **A.** An empty box: 11, 20, 2026, then 11, 00, A | one, on the last key | 11:00 AM: right |
| **B.** From 11:00, typed "30" into the minutes | **one, on the "3"**; the picker closed | **11:03 AM**, saved as `17:03:00Z` |
| **C.** From 11:03, the arrow key on the minutes, 6 times | one, on the first press; the picker closed | moved one step only |

**The cause:**
- **Once the box holds a whole value, Chrome fires `change` on every key.**
- **The component closed the tooltip on the first `change`** (`handleInputChange`), so the next key went nowhere.

**That fits what the maintainer saw:**
- **The cutoff:** retyping the hour "11" over an existing value stops after the first "1".
- **The start, "1:01 AM, then 12:01 AM":** the same one-key cut-off, applied to a time typed from scratch.
- **Four saves:** each try kept only part of what was typed.

**On today's picker, all five fail; the 20 existing tests pass.** The failing run's log is saved on this machine (below).

**To be honest about how they fail:** they fail because today's picker has no separate date and time fields. **jsdom doesn't
implement the `datetime-local` box's per-key `change`**, so the dropped key itself can't be reproduced in a unit test. The browser
run in §1 is that proof.

**The tests assert the moment in local time**: `new Date(2026, 10, 20, 11, 0)`, not `17:00Z`.
- **Why:** setting `process.env.TZ` inside a Vitest worker doesn't change its time zone, and the picker works in the browser's own
  time.
- **The Central-time check:** the browser run in §4 saved `2026-11-20T17:00:00.000Z` from Central, as #2583 asks.

## 3. The change

| File | What |
| --- | --- |
| `date-time-picker.component.ts` | **What the picker picks** is decided by `pickerKindFor`: `time`, `date` or `date-time`. **A date** is `MatDatepicker` with `MatDatepickerInput` and a toggle; **a time** is `MatTimepicker` with `MatTimepickerInput` and a toggle. **A value takes effect on `dateChange` or `valueChange`**, so when a date is chosen, or a typed one is left or entered, never on a single key. **A picker of both stays open after the date** and closes when the list of times closes. **A date alone or a time alone opens its calendar or list at once**, as the time did before. **An emptied date tells the form `null`** and emits no `changed`, which carries a date. **The inputs and the `changed` output are unchanged.** `withDate` and `withTime` replace the `datetime-local` string parsing, keeping #1772's handling of an invalid stored value |
| `date-time-picker.component.html` | a date field and a time field, each with its Material toggle, labelled *Date* and *Time* |
| `date-time-picker.component.scss` | the field rows. **The calendar's colours** go on Material's `.mat-datepicker-popup`, narrowed with `:has()` to this picker's calendar: Material puts a datepicker's `panelClass` on the calendar *inside* the box that draws the background, so on the panel class alone the calendar had no background. The site's table striping is turned off on the calendar's rows |
| `tooltip.component.ts` (layout) | **a click inside Material's overlay (`.cdk-overlay-container`) isn't a click outside the tooltip**, so choosing a day doesn't close the picker before the time is set. Only Material uses that overlay in these apps |
| the spec | the five tests above. The existing tests that used `inputTypeFor`, `toInputValue`, `fromInputValue` and `handleInputChange` now test `pickerKindFor`, `withDate`, `withTime` and the handlers, keeping what each checked |

**Keyboard and screen reader:** Material's own, with the date field's arrow keys and the calendar's keyboard grid, the time list's
arrows and Enter, and labelled toggles. I didn't test with a screen reader.
