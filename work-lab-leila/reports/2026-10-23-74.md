## 3. Options, ranked by time saved per job, all safe from fork pull requests

**The rule under all of them:** anything a later job *reads* must be writable only by a trusted job. The way to make a job trusted is **a second
pool, e.g. `Linux-Build-Trusted`, with an Azure DevOps *branch control* check** (Agent pools → the pool → Approvals and checks → Branch control:
`refs/heads/development` only). A fork can rewrite the pipeline YAML in its pull request to ask for any pool, so the pool's own check, not the
YAML, is what keeps forks out. Fork jobs only ever get **read-only** mounts.

| # | Option | Saves | What a malicious fork job could do with it | Safe? |
| --- | --- | --- | --- | --- |
| 1 | **A warm git repository.** A bare mirror of the repo in a Docker **volume** (not a host folder), refreshed only by a trusted job or a host task fetching from `origin`, mounted **read-only**. `start.sh` copies it into the job's working folder before the checkout, so the checkout only fetches what is new. | **~30 s per job** (36 s → a few seconds), every job | Read it (it is the public repo). It cannot write: the mount is read-only. | **Yes.** Git objects are named by their hashes, and the source is `origin` only. |
| 2 | **A local `node_modules` cache.** A volume of packed `node_modules`, keyed by `package-lock.json`'s hash, written only by trusted jobs, read-only for all others. A fork with a different lock simply misses and runs `npm ci` (28 s). | **The `Cache@2` download** (likely 15 to 40 s; read it from the job log) **minus 4.4 s** to unpack locally, on every job that restores | Read packages already public. Write nothing. | **Yes**, only with the trusted-pool split. A cache forks could write is the textbook poisoning path: a fork plants files under the key a trusted build will use next. |
| 3 | **A fourth agent**, so the third ready job never waits for a re-registration. Three agents at 14 GB and 6 CPUs fit Docker's 62.5 GiB and 24 CPUs; **four fit at 12 GB and 5 CPUs** each (the measured peak is 10.4 GB), leaving 14.5 GiB and 4 CPUs. | **~25 s, once per PR** (the wait production had in 5680) | Nothing new: another identical, isolated agent. | **Yes.** |
| 4 | **Node in the agent image's tool cache** (`$(Agent.ToolsDirectory)/node/24.22.1/x64`, so `UseNode@1` finds it) | **~4 s per job** | Nothing: the image is rebuilt by the maintainer, and each job gets a fresh copy. | **Yes.** |
| 5 | **The npm download cache (`~/.npm`) instead of #2**, in a shared volume | most of `npm ci`'s 28 s on a miss | npm's cache is content-addressed and `npm ci` checks every package against the lock's `integrity` hash, so planted content would be refused. A fork could still fill the disk. | **Read-only for forks, as #2.** Simpler than #2, and it saves less (`npm ci` still links 143,000 files). |
| 6 | **An Nx cache shared between agents** | the work itself, when inputs are unchanged | **Poison it:** an Nx cache replays outputs by the hash of their inputs, and a fork knows those inputs. It could plant a bad `main.js` under the hash `development`'s build will compute, and the trusted build would ship it. | **Only read-only for forks, written by trusted jobs.** Nx Cloud already serves this role remotely; from the lab it cannot store (no token), which is the safe way round. **Recommendation: leave it to Nx Cloud.** |
| - | *A long-lived "warm" container that takes several jobs* | the ~21 s registration | Everything one job leaves behind reaches the next: files, processes, the agent's own credential. | **No.** It undoes `--once`. |
| - | *A shallow clone (`fetchDepth`)* | 6 s (36.4 → 29.9) | nothing | Safe, but `affected` needs the base commit, which may be further back than any fixed depth. **Not worth it.** |

**Together, #1 to #4 should bring a lab job close to hosted on the fixed costs:** about 30 s (git) + the restore + 4 s (Node) per job, and 25
s once per PR. With three or four jobs side by side, **a PR's heavy stages should finish well inside hosted's time**, rather than about 1 minute
faster as in 5680.

## 4. Proposed order

   from a job log. The maintainer adds the pool check in Azure DevOps.
