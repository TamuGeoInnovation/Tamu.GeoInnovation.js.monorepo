## 1. The shared answer: the package name

Every spec tsconfig that named `"../../node_modules/@arcgis/core/interfaces"` (**35**; 30 of them three or four levels deep, where it pointed at
nothing) now names **`"@arcgis/core/interfaces"`**.

- **Why it works everywhere:** an entry in `types` is resolved like a `/// <reference types>`, walking up through `node_modules` from the
  tsconfig's own folder, so one spelling works at any depth. `@arcgis/core` has **no `exports` map**, which could otherwise have refused the
  sub-path.
- **Proven** on `libs/maps/esri` (three deep) before changing the rest: TS2688 gone.
- **Why not the base config:**
  - **`tsconfig.base.json`** has `"types": ["*"]`, and every spec tsconfig sets its own `types`, which replaces the base's, so an entry
    there would not reach them;
  - **`typeRoots`** would change how every project finds `@types`.

  The package name is the smallest shared answer: nothing to count, nothing else affected.
- **The 5 spec tsconfigs whose path already resolved** (two levels deep) use the same spelling too, so there is one way to write it.

**Not changed, the same wrong path elsewhere:** **30 `tsconfig.lib.json`** (and `libs/common/utils/geometry/generic/tsconfig.json`) carry
`../../node_modules/...` from three or four levels deep, in the same libraries as the spec ones. They are read only by a library's own build,
which most of these libraries do not have (apps compile library code under their own tsconfig, whose path is right), so they are inert today.
**Recommendation: the same one-line change, if you want it; a small follow-up batch.** The 15 two-levels-deep ones (apps, editor configs) are
right as they are.
