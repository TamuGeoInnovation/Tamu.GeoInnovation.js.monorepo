## 1. The kiosk: the layer ids come from the definition

**What changed:**
- **One home for the ids:** `TAILGATING_LAYERS`, `DINING_KIOSK_LAYERS` and `TAILGATING_KIOSK_LAYERS` move into a new
  `libs/ts/events/ngx/src/lib/definitions/kiosk-layer-ids.ts`.
  - That file has **no imports**, so Playwright can load it; the definitions themselves can't be imported there (`definitions.ts`
    says why).
  - The three definition files import and re-export the ids, so no caller changes.
- **`kiosk.spec.ts` reads both kiosks' lists from it**, instead of keeping a copy.
- **The failure message now names the layers:** `<route> draws N layer(s) its definition does not list: <ids>`.

**What I found:**
- **A list read from the checkout runs ahead of production.** Production's build (`main-M2EOIZCV.js`) predates #2661, so its kiosk has
  no `tailgating-restrooms`.
- **On the first run, production failed 3 tests:** every tailgating test waited for that layer.
- **The fix follows the suite's own pattern for this:** `environments.json` gets a new production entry, `allowedMissingKioskLayers`
  (`{ "tailgating-restrooms": "#2701: ..." }`), read by base URL as `allowedPopupFailures` is.
  - The check waits for and checks every other layer, and records the gap as a *known failure*.
  - Once production draws the layer, it says *known failure now passing; remove it*.
  - The extras check still uses the whole list.

**Runs:**
- production **7 of 7**, and dev **7 of 7**;
- with `RESTROOMS` taken out of the ids file and run on dev, **1 failed as intended**: *draws 1 layer(s) its definition does not list:
  tailgating-restrooms*. The file was restored afterwards, and the diff checked.

## 2. `?feature=`: what already existed, and the fix

**What I found first, as you asked:**
- **`?feature=` can't take an attribute, but `?lot=043` already opens Lot 043 on both servers**, and so do `?lot=43` and
  `?lot=Lot 043`.
  - It works through the application's `lot` search source, which matches `LotName`, `Name` and `FAC_CODE` against the map's own layer
    (#1952).
  - Both servers hold the lot as `FAC_CODE=043`, `Name=43` and `LotName=Lot 043`; only the object id differs (26135 against 34694).
- **What breaks a copied link is the popup's Copy button.**
  - Its readable link comes from the map's *own* link sources (#1481), and AVP declares none.
  - It also compared field names whole, so even a declared `FAC_CODE` would have missed `GIS.TS.ParkingLots.FAC_CODE`.

**The fix, through #1481's own mechanism:**
- **`parkingLotLinkSource(url)`**, in `common.definitions.ts`: a link-only `?lot=` source matched on `FAC_CODE`. **AVP uses it.** The
  sidebar search is unchanged.
- **`services/event/feature-links.ts`** holds two functions, which both the event service and the popup now use:
  - `fieldMatches`, #1952's last-part rule;
  - `readableLinkIdentity`, the Copy button's choice.
- **Object-id links already shared still work.**
- **The fixtures:** `directions.spec.ts`'s two AVP fixtures move to `?lot=043`.

**The new smoke check** is in `lot-links.spec.ts`. Lot 043's popup must copy `?lot=043`, and the copied link must open Lot 043 again.
- **Before the fix, it failed for the right reason:**
  - **on dev:** *copies .../map/d?feature=AVP-parking-lots:34694, an object id this server alone uses*;
  - **on production:** the same, with `:26135`.
- **After the fix, against this branch on a local dev server:**
  - `lot-links.spec.ts` 6 of 6;
  - `directions.spec.ts` 14 of 14 (and 14 of 14 on dev's deployed build with the new fixtures).
- **The unit tests:** `feature-links.spec.ts` has 8 tests on Lot 043's real joined attributes, run with Vitest: 8 passed.

## Questions for the director (aggiemap)

1. **Should the other parking maps copy `?lot=` too?**
   - **The background:** AVP was the item, but every event map whose lots carry `FAC_CODE` and that declares no link source still copies
     an object id. That object id names the lot on one server only, and changes on a republish.
   - **The options:**
     - **(a)** add `parkingLotLinkSource` to each, one pull request, after checking each service has `FAC_CODE`;
     - **(b)** leave them until each is touched.
   - **Recommended:** (a), as a follow-up issue. It's a definition line per map, and a smoke check like AVP's for a sample.
2. **Should item 2's new check be a known failure on production until the release?**
   - **The background:** it fails on production's nightly run until a release carries the fix, as any regression test does against an
     unfixed build. Item 1 needed an `environments.json` entry for the same reason.
   - **The options:**
     - **(a)** an `allowedPopupFailures`-style entry tied to #2701;
     - **(b)** leave it red until the release.
   - **Recommended:** (b), if the release is soon. It's visible and honest, and the health issue closes itself. Otherwise (a).
3. **Should the readable link be used by more than event maps?**
   - **The background:** `?feature=` itself still can't name an attribute. I didn't add that, because `?lot=` and `?zone=` already
     cover it and a second way of naming a feature would be a one-off. If some map's features have no readable link at all, that's
     where (a) would be needed.
   - **The options:**
     - **(a)** extend `?feature=` to `<layerId>:<field>=<value>`;
     - **(b)** keep naming features through link sources only.
   - **Recommended:** (b), unless a map turns up with nothing readable to link.
