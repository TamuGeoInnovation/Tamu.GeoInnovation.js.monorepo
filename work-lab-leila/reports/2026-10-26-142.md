**The 3D test.**
- **What the app does:** under #1740, a 32139 basemap cannot be drawn in a Web Mercator scene, so in 3D the panel marks it "2D only" and
  ignores a click. That is deliberate, and correct.
- **What the test assumes:** that every *Aggieland* basemap can be chosen in 3D. Until today dev opened on the 32139 basemap and listed it
  first, and the test only ever chose it in 2D.
- **The fix:** the test should skip a basemap the panel marks unavailable, or choose it only in 2D.
- **Coverage lost:** #1740's own check (`perspective.spec.ts:179`) now **skips** on dev, because dev opens on a Web Mercator basemap. Nothing
  in the suite proves the "2D only" behaviour any more.

**The building link.** I compared `?bldg=0468` at the suite's 1280×720 viewport on both environments:
- **Production:** opens on all of Evans with HECC, Peterson and the Annex around it
  ([production](2026-10-26-142/bldg-0468-production.jpg)).
- **Dev:** opens several levels closer, on one corner of Evans with no neighbour in view ([dev](2026-10-26-142/bldg-0468-dev.jpg)).

**I have not established the cause.** The zoom is chosen by `MapService.computeZoomLevel` (`libs/maps/esri/src/lib/services/map/map.service.ts:1168`):
- it maps a selection's size to a fixed zoom (19 or 20) using thresholds that read as degrees;
- in a projected view a selection's extent is in metres;
- so what it returns depends on the view's units and levels, which the basemap sets.

This affects every building link and search result on dev while it opens on this basemap. It affects production only if this basemap is
promoted.

One more thing, from reading the definition: `AggiemapVectorBasemap`'s comment in `basemaps.definition.ts` still says the cache is
"Published in EPSG:32139". The October cache is Web Mercator, so the comment describes the September one.

- **Casing in the result list:** "Tamu", "A&m". The shared search component pipes every result through Angular's `titlecase`

**How I typed matters.** The browser's plain *type* action filled the box but sent no `keyup`, and the search component listens only to
`keyup`. So my first tries looked like a broken search on every map, production's Galveston included. Real key presses showed results at
once.

### 3. The new basemap, compared with September

Same place, Wellborn Road between Simpson Drill Field and the West Campus quad, 1280×800:
- [October](2026-10-26-142/basemap-october.jpg);
- [September](2026-10-26-142/basemap-september.jpg), after zooming back in, because choosing it zoomed the map out
  ([as it landed](2026-10-26-142/basemap-september-on-switch.jpg)).

**My opinion: October is the better map for what visitors do.**

- **It names far more.** October labels the streets a visitor navigates by: Wellborn Rd, Jones St, Old Main Dr, Lamar St, Gene Stallings
  Bl, Joe Routt Bl, Olsen Bl. It also labels the building abbreviations people search for (KEAT, FOWL, CLEM, MOSE, HOBG, CMAT, AEPM, HPCT,
  BICH, KLCT) and places such as West Quad. September, at the same scale, names only a few large buildings and one or two roads.
- **It is cleaner.** September fills several buildings with solid magenta, and its legend doesn't say what that marks. October draws
  every building the same, leaving colour to the selection highlight and the app's own layers. Trees, walks and parking read the same in
  both.
- **Switching between them moves the map.** The two caches are in different projections, so going from one to the other zooms out. A
  visitor never does this, but anyone comparing them in the gallery will see it.
- **The cost is the building link above.** On this basemap a building link and a search result open far too close. That needs fixing
  before October goes to production, whatever is decided about how it looks.
