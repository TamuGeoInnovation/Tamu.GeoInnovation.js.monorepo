## 3. The check, and why it isn't in the branch

**Where it belongs:** `maps.spec.ts` already asks every layer of every map for its service's name, through the probe's
`serviceName`. `layer-titles.ts` already has a verdict for exactly this case, **`declared, same as service`**.

**What turning it on takes:** today that verdict is only annotated. The check is one line: add it to the soft expectation
that already fails on `wrong` and `declared, not shown`. No second mechanism, and nothing in `services.spec.ts` is needed.

**Why it isn't turned on.** I read every map's title verdicts from the dev run's JSON report.
- **What it found:** `declared, same as service` came up **154 times: 77 distinct layers on 73 of the 84 maps.** Among them:
  - `rns-spaces-layer` on every event map;
  - all 28 football gameday layers;
  - Fish Camp's six;
  - High School Graduation's six;
  - the five sustainable-transportation layers;
  - SEC Grounds' six;
  - T-Camp's four;
  - and Aggie Family Parade's and Big Event's, which match on development only.

  Every one is "unreviewed (#1523)" in the registry. #2719 named only the first fourteen.
- **The consequence:** turned on today, the check would turn 73 maps red on dev.
- **It also can't be one rule for both hosts.** Development's names have run ahead of production's, so the same entry is
  "same as service" on dev and a real override on production.

**My proposal (Q-a20-2):** turn the check on only once #1523's sweep has measured the other 77. Make it fail on production
only, where visitors are, and leave it as an annotation on development. The full list of 77 is in my scratch folder, from
the dev run's report, and the director can have it.
