## Why

A diagnostic printed at the moment of failure:

```
{"tooltipVisible":false,"tpOpen":true,"container":false,"hostInFixture":false,"panelExit":false}
```

- **The tooltip had closed** and its container was gone.
- **The time picker was still open.** Its list does not live in the tooltip: Material puts it in its own overlay, so removing the tooltip does
  not remove it.
- **The list closes a moment later.** The component closes it when the tooltip says so, through the tooltip's `tooltipContentVisible`, which is
  `debounceTime(1)` on `isVisible`. The test waited a fixed 10 ms and then looked. On a busy machine the debounce had not fired yet.

So the component does close the list. Only the test looked too soon. The same race was in `open()`: the list opens on the same debounced signal,
and the test waited the same fixed 10 ms for it.

## 2. The fix

- **`until(event, act)`**: does `act`, waits for the time picker's own **`opened`/`closed` output**, then settles as before.
- **`open()`** waits for `opened`; **takes the list away** waits for `closed`.
- The time picker is reached through the component's own `viewChild`. A `DebugElement` query cannot find it while the tooltip is closed, because
  it is not projected yet.

No longer fixed delay. Not `NoopAnimationsModule` either: the list closes in jsdom once `close()` runs, so animation was not what made the test
slow.

**The same pattern elsewhere in the library.** Three other fixed waits, none of them this race, so left as they are:

- **"sets the time … closes when a time is chosen":** the click closes everything synchronously (`_selectValue` → `closed` → `close()`), so the
  `settle()` after it does not wait on anything.
- **"does not open the list before the picker itself is opened":** this checks that nothing happens. A slow machine could only make it pass when
  it should not; it cannot flake.
- **`autocomplete.component.spec.ts`'s 100 ms:** it stages "results arrive after the list has opened", which more load only makes truer.
