## The cause

**Not a missing delete: a delete that matched nothing.** The provider did remove the logo first, with `manager.delete(Asset, logos)`. In
typeorm 0.3.31, an array of **whole rows** is not taken as ids. Each row becomes a `WHERE` on every one of its columns, timestamps
included, and **on SQL Server that matched no row**. The logo stayed, and the sponsor's delete then hit
`FK_98821d8bf60cd7694ecaa84dc99`.

**Shown on a real database**, not only in a mock. A probe script (in the scratch volume, not the repository) used the API's own data
source and **`SponsorProvider.deleteEntities`** against a throwaway SQL Server with `development`'s schema. It created a sponsor with a
logo row and a logo file:

| | Unfixed (red) | Fixed (green) |
| --- | --- | --- |
| The delete the old code builds | `DELETE FROM "assets" WHERE ("updated" = @0 AND "created" = @1 AND "guid" = @2 AND "name" = @3 AND "path" = @4 AND "type" = @5)` | (now by guid) |
| `deleteEntities` | **rejected**: `The DELETE statement conflicted with the REFERENCE constraint "FK_98821d8bf60cd7694ecaa84dc99" … column 'sponsorGuid'` (the issue's error) | **resolved `{"affected":1}`** |
| Sponsor left | **yes** | no |
| Asset rows left | **1** | **0** |
| Logo file left | **yes** | **no** |

That is also why the 500 carried the raw database error: the provider **returned** the transaction's promise from inside its `try`,
so a failure escaped the `catch` written to report it.

## Places, organizations and speakers: **the same fault**

`place.service.ts`, `organization.service.ts` and `speaker.provider.ts` (`images`) delete their assets with the same
`manager.delete(Asset, <rows>)` and the same un-awaited transaction. **So deleting a place, an organization or a speaker that has a
logo or image should fail the same way.** Not run against the database for those three; it is the identical call. **And nothing anywhere
deleted an asset's file**: `AssetsService.saveAsset` writes them under `APP_DATA`, and no code removed them.

## The fix

The asset handling moved into `AssetsService`, so the four providers share one way of doing it, per CLAUDE.md's reuse rule:

- **`AssetsService.deleteAssets(manager, assets)`**: deletes the rows **by guid**, inside the caller's transaction, so they go with
  their owner or not at all. It does nothing for an empty list.
- **`AssetsService.deleteAssetFiles(assets)`**: removes their files **after the transaction commits**, so a rolled-back delete never
  loses a file. A file it cannot remove is logged, not thrown, because the caller has already succeeded, and the rest are still removed.
- **`deleteFileFromDisk(path)`** in `libs/common/node/fs`, beside `writeFileToDisk`: `true` when it removed the file, `false` when there
  was none, and it throws anything else.
- **Sponsors, places, organizations and speakers** call both, and **`await` their transaction**, so a failure lands in their own `catch`
  and becomes the 500 they write.

No schema change and no migration: the fault was in the provider, not the relation.

## The double DELETE

**The page asks for one delete per click.** A new component test renders the edit form, clicks **Delete Sponsor**, and sees
`SponsorService.deleteEntity` called **once**, with the sponsor's guid. `deleteEntity` subscribes once to `httpClient.delete`; no interceptor
retries; the shared button emits once.

**The second request to the same URL is the browser's CORS preflight.** The admin page (`localhost:4201`) and the API (`3333`) are
different origins, and the DELETE carries an `Authorization` header. So the browser first sends `OPTIONS /api/sponsors/<guid>`, which the
API answers **`204`** with `Access-Control-Allow-Methods: GET,POST,PATCH,DELETE` and `Access-Control-Allow-Headers: authorization`
(checked with `curl` against the API built from this branch). A network list shows both against the same URL. **That cannot be removed
from the page across origins**, and it is harmless. The test stays, as a guard that the form never does send two.

I could not watch the real page do it: the admin pages need a sign-in, which I do not have here, as the batch says. **When you run the
admin delete, the network panel's Method column should show `OPTIONS` then `DELETE`.** If it shows two `DELETE`s, I am wrong about this,
and the cause is above the component.
