## 2. The pipeline: lab first, hosted fallback

- **Setup → Last SHA** (hosted, as before) gets one more step, ***Choose the lab or the hosted pool*** (`name: lab_pool`). It runs
  `GET {org}/_apis/distributedtask/pools?poolName=Linux-Build`, then `GET .../pools/{id}/agents?includeCapabilities=false`, with
  `$(System.AccessToken)`, and counts agents with `status == "online"` and `enabled`. It sets the output **`labOnline`** to `true` when there
  is at least one. **Every failure answers `false`**, with a warning naming it: `useLab` off, pools not listable (the Reader grant), no pool
  visible, agents not listable, none online. A 20 s timeout applies to each call.
- **Each heavy job comes from its template twice**: `cacheOrRestoreDependencies.yml`, `lintProjects.yml`, and `build.yml` for development and
  production each. The templates take a typed boolean `lab`:

  | `lab` | Pool | Condition | Job id | Display name |
  | --- | --- | --- | --- | --- |
  | `true` | `name: Linux-Build` | `and(succeeded(), eq(stageDependencies.Setup.Last_SHA.outputs['lab_pool.labOnline'], 'true'))` | `…_lab` | `… on lab` |
  | `false` | the pipeline's hosted pool, as today | `and(succeeded(), ne(…, 'true'))` | as today | **as today** |

  The conditions before were all the default `succeeded()`, which both twins keep; the affected/deployable logic is in the steps and is
  unchanged. **Exactly one twin of each pair runs; the other is *Skipped*.**
- **`useLab: true`** under `variables:`; **`useLab: false` is the one-line switch back to all-hosted**, documented in the README.
- **Dependencies** already depends on Setup (a stage with no `dependsOn` depends on the one before it), so its jobs can read Setup's output.
  Lint and Build name Setup explicitly, as before.

**What the stages and GitHub will see** (from the YAML; not yet seen in a real run):

- The **Tag** stage (`dependsOn: Setup, Build`, `succeeded()`): a stage whose only non-skipped job succeeded is *Succeeded*, so Tag runs as
  today.
- The overall result, and **the `Monorepo` check**, is *Succeeded* when every job that ran succeeded; a skipped twin does not fail it.
- **Per-job checks**: on a lab run, `Monorepo (Dependencies Cache or Restore on lab)`, `Monorepo (Lint Lint Affected on lab)`, `Monorepo (Build
  development on lab)` and `Monorepo (Build production on lab)` report the result, and today's four names report *skipped*. On a hosted run it
  is the other way round: **today's names report as today, and the `on lab` names are skipped.** `Monorepo (Setup Last SHA)` is unchanged.
- **`development` has no required status checks on GitHub.** Branch protection's `required_status_checks` is off, and the only ruleset is
  Copilot review. So nothing on GitHub blocks on any of these names; "required" for `Monorepo` is the team's practice (CLAUDE.md). If a
  required check is added later, **`Monorepo` is the one name that means the same on both pools.**
- **Artifacts** keep their names (`js-monorepo-development`, `js-monorepo-production`), since only one twin publishes; releases are unaffected.

**Not proven here:** the YAML parses (every file), but Azure's template expansion (`iif`, `${{ else }}`, typed parameters, the cross-stage
condition) can only be confirmed by Azure. **The PR's own run is that test.** If it fails to expand, Azure says so before any job starts.

   it). Nothing in an agent container listens on a port, so a fork job has nothing to connect to in a sibling. But a branch build next to it
   has `app_configs` on disk. Options: (a) accept it; (b) one internal network per agent, each joined to the same proxy, a small change to
