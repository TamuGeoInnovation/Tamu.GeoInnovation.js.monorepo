The full table is `basemap-failure-rate.txt` in this report's folder.

### Whether a failing layer still returns its features

**Yes. Nothing returns short.**
- **How:** for every layer I compared its object-id list (`returnIdsOnly`) with every feature fetched page by page.
- **The result:** they matched for all 58, including:
  - layer 5, Off Campus Building: **94,007 = 94,007**;
  - layer 8, Parking Line: 58,398;
  - layer 1, Structure Data: **1,003**;
  - layer 2, University Building: 1,802;
  - layer 9, Surface Parking: **341**.
- **When a request fails, it fails whole**, with the 500. It doesn't return a partial answer.

**One trap for anyone repeating this:** several layers don't call their id field `OBJECTID` (layers 11 and 13 use `OBJECTID_1`; 19,
20, 60, 63 and 64 use `OBJECTID_12`), and the service doesn't publish `objectIdField`. Asking for `outFields=OBJECTID` answers
`400 Failed to execute query`, which looks like this fault and isn't. My first walk mistook it for one.

### What that does to a real map

**The measurement:** production's main map (`aggiemap.tamu.edu/map/d`), loaded 10 times, with every basemap query recorded:

| | |
| --- | --- |
| basemap queries per load | **36**: 12 each to layers 1 (Buildings), 2 (University Building) and 9 (Surface Parking) |
| loads with a failed query | **5 of 10** (loads 2, 5, 6, 7 and 9) |
| failed queries | 5 of 360: layer 1 twice, layer 2 twice, layer 9 once |
| retried | **no:** every load sent exactly 12 per layer, so a failed one wasn't asked again |

**What that means:** the map fetches each layer as tiles. On half of all loads, one tile of buildings or parking lots fails and isn't
retried, so that load most likely draws without it. **I didn't confirm the missing tile on screen**; this is the request evidence only
