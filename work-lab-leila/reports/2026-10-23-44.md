## 3. The conversion, and what it took

- **`nx g @nx/webpack:convert-to-inferred` refused**: every config uses `composePlugins`/`withNx`. **And
  `nx g @nx/webpack:convert-config-to-webpack-plugin` refuses Nest apps outright**: `validate-project.js` rejects any project with an
  `@nx/js:node` target, and all six have one (`serve`).
- So **each `webpack.config.js` was put in the shape `convert-config-to-webpack-plugin` would have written**: a `const options = {}`, and
  `NxAppWebpackPlugin(options)` beside `useLegacyNxPlugin(require('./webpack.config.old'), options)`. **`convert-to-inferred` then ran
  cleanly**: it moved each `project.json` build target's options and configurations into the config as `configValues`, picked by
  `NX_TASK_TARGET_CONFIGURATION`, made the paths project-relative, and left empty `production`/`development` configurations in
  `project.json`. It also registered `@nx/webpack/plugin` in `nx.json` with a filtered `build` default for its outputs, and **added
  `webpack-cli` ^7.0.0** (question 1).
- **Then, as Nx 24's AI prompt for this migration says** (`tools/ai-migrations/@nx/webpack/24.0.0/migrate-compose-plugins.md`, read
  from batch 44's probe volume): what each old config still did was moved into the new one, and the `.old` files and
  `useLegacyNxPlugin` were removed. Five old configs did nothing (`composePlugins(withNx(), (config) => config)`). **`gisday-nest`'s**
  set `devtoolModuleFilenameTemplate` (with its logging) and `output.path`.

**First comparison: different, and not harmlessly.** Each difference came from webpack now running in the project folder (the inferred
target's `cwd`), or from the plugin choosing defaults by `NODE_ENV` where the executor had its own:
