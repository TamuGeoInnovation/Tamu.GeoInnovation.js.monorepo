## 1. Reuse first

**`libs/common/**` has no id or UUID helper.** The only near hit is `isOwnerOrPermitted`, which compares guids but does not make or check them.
But **`class-validator`**, which the Nest code already depends on (`0.15.1`, three files in the same library import it), **exports `isUUID`**.
So the one `validate` call needed no new code, and **no helper was added**. The batch asked for a shared helper with a unit test; reusing the
existing function is what CLAUDE.md's rule asks first, and I'd rather not add a second copy of something a dependency already has. If you still
want our own helper (to keep `class-validator` out of front-end code one day, say), it is ten lines.

## 2. The change

- **23 `v4()` calls in 16 files** → **`crypto.randomUUID()`**, and the `import { v4 as guid } from 'uuid'` lines removed:
  - AggieMap: popups, desktop and mobile sidebars, report-bad-route, bus route;
  - the trip planner: two components and two services;
  - ui-kits: copy, draggable, search;
  - the notification container and grouped notifications;
  - **GIS Day's `GuidIdentity`** in both data APIs (`all.entity.ts`, `all.entities.ts`), which gives every row its guid before insert.
- **`submission.controller.ts`**: `validate as isUuid` from `uuid` → **`isUUID` from `class-validator`**, same call site.
- **`uuid` removed from `package.json`.** No `@types/uuid` was listed.
- **The lock**: only the root's `dependencies` list changed. **`uuid` stays installed** as `bull`'s, `sockjs`'s, `typeorm`'s, `auth0`'s and
  `jest-junit`'s own dependency.

## 3. Where `crypto.randomUUID()` runs

Browsers provide it only in a secure context (HTTPS, or `localhost`/`127.0.0.1`); Node 24 always does.

| Code | Runs in | Secure? |
| --- | --- | --- |
| GIS Day entities | Node 24 (the APIs) | always available |
| AggieMap components, trip planner, bus route | the browser, at `https://aggiemap.tamu.edu`, `https://dev.aggiemap.tamu.edu`, or a local dev server on `localhost` | yes |
| ui-kits (copy, draggable, search) and notifications | every front end that uses them | yes, as far as the repository shows |

**What I cannot see:** the front ends' `nginx.conf` listens on port 80 inside the container, so TLS is handled by whatever sits in front of
them. **If any front end (geoservices, mailroom, signage) is reached over plain `http://` on a host other than localhost, those four shared
components would throw there.** The smoke suite's environments are all HTTPS, and nothing in the repository serves a plain-HTTP public address.
**Worth one line from someone who knows the hosting.**
