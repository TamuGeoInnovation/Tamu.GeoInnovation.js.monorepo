## What "finished" meant, call site by call site

| Call site | Waited for | Timeout | Now |
| --- | --- | --- | --- |
| `popup.spec.ts` `openMap` | `ready`, then (a second wait) `drawing === false` | 90 s + 60 s | `waitForMapReady`, then `waitForMapDrawn(…, { timeout: 60_000, ready: false })` |
| `building-clicks.spec.ts` `openMap` | the same two steps, as a loop | 90 s + 60 s | the same two calls |
| `kiosk.spec.ts` `finishesDrawing` | `drawing === false` **only** | 90 s | `waitForMapDrawn(…, { ready: false })` |
| `kiosk.spec.ts` `drawnLayers` | `ready` and `drawing === false`, then the layers | 120 s | `waitForMapDrawn(…, { timeout: 120_000, until: () => true })` |
| `layer-order.spec.ts` | `ready` and `drawing === false` at one reading, and both layers listed | 90 s | `waitForMapDrawn(…, { until: both listed })` |
| `selection.spec.ts` | `ready` and `drawing === false`, and the selection layer has graphics | 90 s | `waitForMapDrawn(…, { until: a feature selected })` |
| `legend.spec.ts`, the main map | `ready` and `drawing === false`, polled every animation frame | 180 s | `waitForMapDrawn(…, { timeout: 180_000 })`, polled each second |
| `legend.spec.ts`, Freshman Selectable Parking | `drawing === false` **only**, after the legend lists a layer | 120 s | `waitForMapDrawn(…, { timeout: 120_000, ready: false })` |
| `map-layers.spec.ts` | a builder redirect, **or** `ready` and `drawing === false` and an `<arcgis-map>` element | 240 s | unchanged, but takes the probe's name from `PROBE_GLOBAL` (why below) |

**The three disagreements:**

1. **Drawing alone can read as finished before the map exists.** The probe's own `drawing` getter returns `false` when
   there's no view (`libs/maps/esri/.../map-probe.ts`: "With no view there is nothing being drawn, which is reported as
   'not drawing'").
   - **Where it matters:** `kiosk`'s `finishesDrawing` and `legend`'s Freshman Selectable Parking test wait on nothing
     else. Each is guarded by something before it (the kiosk has already seen the map ready, and the legend already lists
     a layer), so neither is wrong today.
   - **The risk:** the wait itself would pass on a page with no map.
2. **`ready` isn't one-way.** It's `layersSettled() && framing readable`, and `layersSettled` goes false again for 2 s
   whenever a layer is added, and while it loads.
   - **Two separate waits:** "ready, then drawing" (`popup` and `building-clicks`) can end with a late layer still
     loading.
   - **One reading:** "ready and not drawing at the same reading" (`layer-order`, `selection`, `kiosk`) can't.
   - **The result:** the same map can pass one spec's idea of finished and not another's.
3. **The clocks start in different places,** which is the one that bears on #3369.
   - `popup` and `building-clicks` give 90 s to be ready and then a fresh 60 s to finish drawing: up to 150 s in all.
   - `layer-order` gives 90 s for everything, from `domcontentloaded`.

   So a map that takes about 100 s passes the popup checks and fails `layer-order`. It fails as "never finished drawing
   both layers", which reads like a drawing bug rather than a timeout. #3473 says event maps take up to 73 s; under
   load, that's within reach of `layer-order`'s single 90 s and well within `popup`'s 150 s.

   **Tonight on a quiet machine:** `/parking/indoor-track-parking/map/d` loaded in 16 to 19 s per load, before and after.
   So nothing here reproduces #3369. That fits it being a time budget that runs out under load, not a map that never
   finishes.

**What I didn't change, because each is a decision, not a tidy-up:**
- making the three drawing-only waits require `ready`;
- giving the waits one timeout;
- timing a single budget from one starting point.

- **`waitForMapDrawn(page, message, { timeout = 90_000, ready = true, until })`:** polls each second and returns the layers
  that `until` accepted.
  - **`ready: false`** keeps a drawing-only wait as it was, and each such call site says why.
  - **The feature-count snapshot** is taken only when `until` is given. `snapshot()` asks every layer for its count over
    the network, so it isn't polled where nobody reads it.

**Left alone:**

**One small change in how a wait is polled:** `legend`'s main-map wait used `waitForFunction`, which polls every

later; what it waits for and its 180 s are unchanged. Say if you'd rather it stayed a `waitForFunction`.

## Questions for the director (aggiemap)

**Q-a18-1: Should the three drawing-only waits also require `ready`?** These are `kiosk`'s `finishesDrawing`, `legend`'s
Freshman Selectable Parking test, and the second step of `popup` and `building-clicks`.
- **(a)** Yes, drop `ready: false`. On its own, a drawing-only wait passes on a page with no view, and can pass while a late
  layer loads.
- **(b)** Leave them as they are.

**I recommend (a), as its own small change.** It can only make those waits stricter, never looser, and the option then
goes too.

**Q-a18-2: #3369's budgets.** `layer-order` and `selection` give 90 s from page load, while `popup` and `building-clicks`
give up to 150 s.
- **(a)** Give `layer-order` and `selection` the same budget as the popup checks: 90 s ready plus 60 s drawn, as two waits.
- **(b)** One timeout for every `waitForMapDrawn`.
- **(c)** Measure first, by running `layer-order` under a release tier's load and recording when indoor-track-parking
  finishes.

**I recommend (c), then (a).** Tonight's quiet-machine numbers (16 to 19 s) can't tell a budget from a bug, and #3369 fails
under load.
