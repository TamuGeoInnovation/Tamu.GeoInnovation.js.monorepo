### The five lot-links failures

**The app is right and the test asks the wrong host.**
- The link `?lot=100j` opens lot 100j on dev, and the popup's share link carries **`Visitor Parking Lots:34769`**.
  That's 100j's id in **development's** `TS/VisitorParking` layer 1, the layer dev draws since #2667.
- The test expected **26338**, which is 100j's id in **production's** `TS_Events/VisitorParking`.
- Motorcycle Parking is the same: 15548 opened, 26692 and up expected.
- **The reason:** `lot-links.spec.ts` builds its expected ids from the default `Connections`, which resolves to
  production's hosts in the test process. `search-sources.spec.ts` uses `Connections(gisHostFor(BASE_URL))`, the
  environment's own host.
- The fifth test opens a `?feature=` link with production's id on dev, which can't open there.

**They aren't this build's.** They failed identically in my first run, on `main-332CAWUY.js`, and they must have failed
on dev since #2667 deployed (6 November). They'd pass on production.

**The fix:** in `lot-links.spec.ts`, read the two URLs from `Connections(gisHostFor(BASE_URL))`. The `?feature=` test
then needs its id from the same place, or `test.skip` where the hosts differ, because a `?feature=` link doesn't carry
across environments since #2667 (report 10). I haven't changed anything; it's yours to give out.
