## What this changes

A UES user reported, on UES's dev deployment, that a building search took about five minutes. The search shows
nothing until **every** source has answered, and seven of its sources asked a host that accepts no connection, so
each search waited for those requests to time out.

**The seven sources, and what each pointed at:**

| Search source | Was | Now, on `Production_UES_Operations_Map` (the service the map draws) |
| --- | --- | --- |
| Domestic Cold Water | `ues-arc.tamu.edu/.../Yoho/UES_Operations/MapServer/1` | layer 1, Domestic Cold Water |
| Well Sites | `.../MapServer/5` | layer 6, Well Sites |
| Fire Hydrants | `.../MapServer/6` | layer 7, Fire Hydrants |
| UES Natural Gas Meters | `.../MapServer/29` | layer 38, UES Natural Gas Meters |
| Generators | `.../MapServer/38` | layer 51, Generators |
| Transformers | `.../MapServer/39` | layer 52, Transformer (**not searched**, below) |
| Electrical Manholes (two searches) | `.../MapServer/41` | layer 54, Electrical Manholes |

`ues-arc.tamu.edu` accepts no TCP connection (measured from the lab on 26 November: no connection, then a timeout after
21 s with curl; the browser's requests were refused only after up to 42 s). It is not #2670: **none of the seven is

Required on production, which is theirs; the only searches that read them (`all-parking`, `visitor-parking`,
`one-parking`, `bike-racks`) are already not active, so they cost a search nothing.

**Why repoint rather than drop.** The map already draws these layers from `Production_UES_Operations_Map` on
`pgis-arc-p1.apogee.tamu.edu`, the same server the app signs in to. Each new layer was checked by name and for the
fields its search reads, and has records (8,344 / 12 / 708 / 196 / 180 / 772 / 658). So the searches now find what the
map shows, rather than nothing. One constant, `Connections.uesOperationsUrl`, now serves the map and the searches, so
they cannot drift apart again.

**Three searches needed more than a new address**, each because a query naming a field the layer lacks, or `UPPER()` of
a number, fails the whole query:

- **Fire Hydrants:** `'ASSETNUM '` (with a trailing space) is not on the layer; dropped. `HYDR_NUMBER` is searched.
- **Generators:** `AIM_ASSET_NUMBER` is a number on this layer; dropped. `UES_ID` is searched.
- **Transformers: not searched for now.** The layer has neither `UESID` nor `AIMNumber`, and which of its fields
  (`Number`, `ID`, ...) is the one UES searches by is UES's to say. Turning it back on is one line.

**What a visitor now experiences:** a search lists its results in about 1.5 seconds, including UES's own assets.

**Found, not changed here:**

- **Domestic Cold Water** searches `OBJECTID` and **Natural Gas Meters** `Meter_Number`, both numbers, with
  `UPPER(...) LIKE`, which the service refuses (400). They now fail at once instead of after a timeout, but find
  nothing. Whether they ever worked cannot be told, since the old host never answers. Searching a number needs a
  different where clause, which is a change to these two searches' behaviour, not to their speed.

  longer resolves. They fail at once, so they cost a search no time.

## Body: fix/2421-ues-legend-visible

Title: fix(maps-feature-legend): A legend without visibility toggles leaves out a group's children that are switched off

Closes #2421

## What this changes

A UES user reported, on UES's dev deployment, that the legend displays every feature whether visible or not. Reproduced:
on load the legend has **137 entries**, every UES utility layer among them, although no UES layer is switched on.

**Why.** UES Operations uses the shared `tamu-gisc-legend`. A legend without visibility toggles lists what the map
draws (#1871), and the legend service holds the top-level layers to that. But it keeps hidden layers in its list on
purpose (`respectLayerVisibility: false`), and `LegendCollectionComponent.visibleChildGroups` listed every child of a
group, on or off. UES's layers are all in groups, so the legend listed all of them.

**The fix**, in the shared component: in a legend without toggles, a group's child that is switched off is left out,
at every level, the same rule its top-level layers already follow. A legend that toggles (the event maps') keeps every
child, so a child switched off from its title collapses rather than leaves, as before. A `listHeading` group is
unchanged.

To the questions in #2421:

1. **It followed visibility for top-level layers only**, never for a group's children: a missing filter, not a broken
   binding.
2. **A layer toggled in the layer list is followed now**: switched on, it joins the legend; switched off, it leaves.
3. **Not specific to the test environment**: the legend is the same component on every build.

**Other maps.** The only legends without toggles are UES's and AggieMap's main map. AggieMap's lists no groups of
layers, so it is unchanged. Every event map's legend toggles (their configuration defaults `legendAllowVisibilityToggle`
to true), so none changes. (The fix commit's message says Move-In would change; it does not, and the release entry says
so.)
