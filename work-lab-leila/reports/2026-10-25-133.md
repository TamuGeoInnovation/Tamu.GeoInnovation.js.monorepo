## Why it was intermittent: measured

On the throwaway `lab147` stack (the seed, migrated, on SQL Server 2022) I created six sponsors with a logo through Admin → Sponsors. The "before"
API was `development`'s typeorm 1 code: batch 146's image of `d181a4a57`, whose delete code is unchanged on `development` today. I read each
logo row's stored timestamp, then deleted the six through the admin page:

| Sponsor | logo row `created` | delete on `development` |
| --- | --- | --- |
| REL147 1 | 20:58:32.**380**0000 | **200** |
| REL147 2 | 20:58:47.**180**0000 | **200** |
| REL147 3 | 20:59:02.**190**0000 | **200** |
| REL147 4 | 20:59:17.**123**0000 | **500**, FK_98821d8bf60cd7694ecaa84dc99 |
| REL147 5 | 20:59:32.**083**0000 | **500**, the same |
| REL147 6 | 20:59:46.**973**0000 | **500**, the same |

**The deletes that pass are exactly the ones whose millisecond ends in 0.** The API stores the timestamps at whole milliseconds, but the
timestamps the delete compares against don't survive the round trip as parameters. On the same server:

```
2026-10-25 20:58:32.380 as datetime -> 20:58:32.3800000   matches
2026-10-25 20:59:17.123 as datetime -> 20:59:17.1233333   does not match
2026-10-25 20:59:32.083 as datetime -> 20:59:32.0833333   does not match
```

`datetime` keeps 1/300 s. A time on a whole 10 ms survives rounding to it; any other becomes .xx33333 or .xx66667 and no longer equals the
stored `datetimeoffset`.
- **The behaviour matches the Date parameters being sent as `datetime`.** I did not trace the exact parameter type in the driver; the six
  outcomes, and the SQL above, are the evidence.
- **So on `development` a sponsor with a logo deletes about one time in ten**, whenever the logo was saved on a .xx0 millisecond. That is why
  it passed on `sha-e9e416e` (on `work` and in my batches 141 and 144) and failed on `sha-e8ba974`.
- **typeorm 0.3 did the same** (batch 59 found it there), so this is not new in typeorm 1.

## A bug the batch 59 fix would have caused: shared files

All six sponsors above uploaded `small.png`, and **there was one file on disk.**
- **Same-named uploads share one file:** sponsor, place and organization logos are stored under their upload name, with no prefix.
- **The placeholder is shared too:** on the seed, **930 asset rows point at `images/placeholder.svg`**, the seeded speakers' photo.
- **What `433a090f5` did:** its `deleteAssetFiles` removed an owner's file whoever else used it. Deleting one sponsor would have removed the
  logo of every sponsor with the same file name. Deleting one seeded speaker would have removed the placeholder for every speaker on the site.
- **The fix (`f3a8f7eec`):** after the delete commits, a file is removed only if no remaining asset row names its path.

**Red** at `51c0c7def`: *keeps a file that another asset row still uses*, with `Expected: not "/srv/gisday-assets/images/placeholder.svg"`.
**Green** at `f3a8f7eec`.

**Not fixed here:** sponsor logos overwrite each other on upload already: two sponsors who upload `logo.png` share one file. That is a
separate bug, and the question below asks about it.
