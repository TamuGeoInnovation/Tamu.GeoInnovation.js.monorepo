## It was more than the URL

Layers 0 (Bus Stops, multipoint) and 1 (Bus Routes, polyline) keep their indices, and the route colours come from the
same `uniqueValue` renderer. So #2209's index trap isn't here. Four other things differ, and each would have broken
the map silently:

1. **The field names are lower case.** The view answers the old names with an error, `Field name 'RouteNum' does not
   exist. Did you mean 'routenum'?`, and returns it with HTTP 200. `BusService` catches only HTTP errors, so a URL-only
   change would have shown an empty bus panel and logged nothing. `BusService`, the `?busstop=` source and the stop
   popup now use the view's names.
2. **Route 47 has a `stop32` on production** ("32. Wehner - Inbound"). Development's view stops at `stop31`. Naming 31
   fields drops that stop on production; naming 32 fails the query on development. The stops are now read from
   whichever `stopN` fields the answer has, in number order.
3. **The stop ids are new, and not the same on both hosts:** 1 to 212 on development, 4214 to 4817 (with gaps) on
   production, for the same 212 stops (I matched all 212 by name, route, number and position).
   - A `?busstop=` link opens its stop only on the environment it was copied on, and one copied from the old service
     (4718 and up) opens nothing.
   - No other field identifies a stop: `stopnum` + `route` still has 3 duplicates. So the link stays on `objectid`.
   - The smoke suite's two `?busstop=4719` tests (`search-sources.spec.ts`, `directions.spec.ts`) now take Blinn's id
     from global setup, which asks the environment's own service for it, as it already reads the bus routes.
4. **Routes 47/48 and 48 are gone:** 23 routes, not 26. Their #1174 allowance goes from `environments.json`.

**The title overrides:** none to remove. The bus layer is drawn by `BusService` as a graphics layer, with no `title`
overrides for stops or routes.

**`gis-dev.it.tamu.edu`:** the batch says no other code reads it, but it's the development `gisHost` itself: the FCOR,
BikeMap and `RoutingProPublish` services are read there. What was wrong was reading it on every environment. This
change takes the bus routes off it entirely; `RoutingProPublish` stays pinned there, as before.

**How `BusService` gets the URL:**
- It can't import `Connections`, so a new `BUS_ROUTES_URL` token carries the URL. AggieMap provides it from
  `environment.Connections`, the same connections the `?busstop=` search source is built from.
- My first version provided it from the browser's address instead. The live check caught it: on the local serve, the
  routes read development's view while the stop link read production's, and the link opened nothing.
- Anything that doesn't provide the token reads production's view. `ues-operations-angular` is the other app using
  `BusService`, and its build is in the check.

**The tests:**
- **`connections.spec.ts`:** a new test that each environment reads its own view. It fails on the old code, which

## Questions for the director (aggiemap)

1. **The two `?busstop=` smoke tests between merge and release.**
   - **Background:** once this merges, global setup asks the new view for Blinn's id (2 on dev, 4215 on production),
     while each deployed build still reads the old service, where those ids don't exist. So
     `bus-stops-exact` and the directions "bus stop" case fail on each environment's nightly until it carries this
     build.
   - **The options:**
     - **(a)** let them fail; the health issue says why, and it closes on the first run after each deploy;
     - **(b)** list them as known failures tied to #2636 until each release.
   - **Recommended:** (a) for dev, which deploys soon after merging. If production's release is more than a day or two
     behind, (b) for production, because a nightly failure nobody acts on trains people to ignore it.
2. **Stop links copied before the release.**
   - **Background:** `?busstop=` links copied from AggieMap until now carry the old ids. After the release they open no
     stop on any environment. The bus panel is development-only, but the `?busstop=` source is on production's main map
     too, so a link copied from a dev popup could have been shared.
   - **The options:**
     - **(a)** accept it;
     - **(b)** a one-time map of the 210 old ids to the new ones, by name, route and stop number.
   - **Recommended:** (a). The ids moved with Transportation's republish, not with our change, and the next republish
     will move them again. A map would fix one generation of links and give a false sense that links are stable.
3. **Whether to file the duplicate ids as a question for Transportation.**
   - **Background:** a stable stop id (`stopnum` that is unique, or a stop code) would make `?busstop=` links survive a
     republish and work across environments.
   - **The options:**
     - **(a)** file it as a request to Transportation;
     - **(b)** none.
   - **Recommended:** (a), at low priority.
