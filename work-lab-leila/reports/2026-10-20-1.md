**Maintenance Parking is not slow; the limit is tracking machine load.** On 24 CPUs it passed every time, and

| Run | Command | Workers | Maintenance Parking | Service Parking (`/parking/service-loading`) |
| --- | --- | --- | --- | --- |
| 1 | `run-local.sh production one map-layers.spec.ts --retries=0` | 6 (the local default) | passed, 41.5 s | passed, 1.1 min |
| 2 | the same with `--workers=6` | 6 | passed, 46.6 s | passed, 1.1 min |
| 3 | `run-local.sh production one maintenance-parking --retries=0` | the 3 Maintenance Parking tests, one per spec | passed, 43.4 s | not run |

The failing runs recorded on 20 October took 134 and 147 seconds for these two maps with six workers, and
failed the 240-second limit outright on two other machines. Here, the same worker count makes no measurable
difference (41.5 and 46.6 s against 43.4 s alone). So the wall-clock number measures how much CPU the machine
has to spare, not how long the map takes to draw.

**What the suite should do instead.** It already has the mechanism: `@heavy` (#1716) runs tests that need
the machine after everything else, two at a time. Tag the two maps that load every parking space on campus,
Maintenance Parking and Service Parking, as heavy in `map-layers.spec.ts`, so they no longer settle against
five other map loads. This keeps the 240-second limit as a real "this map has become slow" signal, which a
longer clock would hide. Alternatively, scale the limit by worker count, but that turns a fixed claim into a
guess about the machine. I recommend `@heavy`.

## The `CLAUDE_SETUP.md` Phase 5 finding

- **Symptom:** following Phase 5 on this machine, the AggieMap dev server compiled and answered on port 4200,
  but the page stayed blank. The log stopped at `[vite] (client) [optimizer] bundling dependencies...` and
  never moved; the cache folder held only `deps_temp_*`. After a `docker rm -f`, the next start printed
  `Waiting for aggiemap-angular:serve in another nx process` and never continued.
- **What the two settings change:**
  - `UV_THREADPOOL_SIZE=64`: `--poll=2000` keeps Node's four default file-system threads busy polling the
    Windows bind mount, and Vite's dependency optimizer waits behind them forever. More threads give it room
    (#1955).
  - `NX_WORKSPACE_DATA_DIRECTORY=/tmp/nx-workspace-data`: keeps Nx's running-task records inside the
    container. In the checkout's `.nx/workspace-data`, a record left by a killed container makes the next
    serve wait for itself (#1626).
- **Specific to this machine?** No. Anyone following Phase 5 or GETTING_STARTED.md Path 5 on Windows hits it:
  both come from the bind mount and `--poll`, not from this hardware. `docs/gisday-local.md` already
  describes both for `gisday-dev`, and `scripts/gisday-local.sh` sets both. Only the AggieMap commands in
  `CLAUDE_SETUP.md` and `GETTING_STARTED.md` leave them out. `CLAUDE.md`'s own `aggiemap-dev` command (in "Keep a
  dev server's install current") has the same gap.
- **The fix:** `fork/docs/aggiemap-dev-server-env` at `fff53ee7` (on `danielgoldbergtamu`) adds both settings,
  with a note on each, to the two setup documents. It does not change `CLAUDE.md`. No issue, no pull request.
