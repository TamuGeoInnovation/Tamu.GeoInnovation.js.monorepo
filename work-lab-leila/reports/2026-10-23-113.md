## 2. Proof that it works, not only that it builds

Batch 114's harness: a throwaway token issuer on a private Docker network, with keys made at start-up and never saved, and tokens handed only to
a client on that network, never printed or written down. The stack was a throwaway SQL Server with the seed and `migration-run`, plus Redis,
under `lab126-*` names. The GIS Day stack already running here was not touched.

The issuer serves the JWKS of **one key**, and signs five kinds of token: good; signed by **a second key** under the same `kid`; for **another
audience**; **expired**; and none at all. Each went as a real request to a sign-in-guarded route, `POST /api/organizations` (`JwtGuard` and
`create:organizations`), on two **gisday-nest production images**, built as `publish.yml` builds them:

| Request | before: batch 125's base, `jwks-rsa` 2.1.5 (as `development`), `jose` 2.0.7 | after: this branch, `jwks-rsa` 4.1.0, `jose` 6.2.13 |
| --- | --- | --- |
| no token | 401 | **401** |
| **good token** | 201 | **201** |
| **signed by another key** | 401 | **401** |
| for another audience | 401 | **401** |
| expired | 401 | **401** |
| good token again (the key now cached) | 201 | **201** |
| API state after | running, 0 restarts, 0 error lines | **the same** |

So 4 fetches the JWKS, verifies a good signature, and refuses one made by a key the JWKS does not hold. `passport-jwt` still refuses the wrong
audience and an expired token. The test took about 10 minutes, well within the hour.

**Cleaned up:** the containers, their network, the two test images, and the scratch settings files holding the throwaway database's passwords.
