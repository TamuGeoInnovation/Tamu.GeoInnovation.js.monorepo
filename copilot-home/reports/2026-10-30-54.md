## The cause

All 68 `created`/`updated` columns defaulted to `getdate()`, the database server's local time. A `datetimeoffset` column stored it with `+00:00`. TypeORM also hard-codes `"updated" = CURRENT_TIMESTAMP` on every update (`repository.update`, and `save` of an existing row), which SQL Server reads the same way. So a database server on Central time stores every time 5 hours early (CDT) or 6 (CST). The local `gisday-db` container is UTC, which hid it.

## What changed

1. **Both, DB and API** (your "which and why"):
   - **Database default `SYSDATETIMEOFFSET()`** on all 68 columns (the base `TimeStampEntity` and `GISDayCompetitionBaseEntity`, through one constant, `DATABASE_NOW`). Any writer that is not TypeORM, including the old API's inserts, is right.
   - **API-side `UtcTimestampSubscriber`** (`libs/gisday/platform/data-api/src/lib/entities/utc-timestamps.ts`, registered in `app.module.ts` as `GISDAY_SUBSCRIBERS`): stamps `created` and `updated` from Node's clock (UTC) on insert if not given, and always `updated` on update. A default alone cannot fix updates, because TypeORM writes its own `CURRENT_TIMESTAMP` unless `updated` is among the values being set. The subscriber sets it, so TypeORM omits its own. It also makes the VGI scoring test deterministic with fake time.
2. **Migration `1793389420957-UtcTimestamps.ts`**: 68 DROP/ADD CONSTRAINT pairs. `down` restores `getdate()`. The generator emits a no-op `ALTER COLUMN "updated" datetimeoffset NOT NULL` before each `updated` default change (136 such statements in all); harmless, kept as generated rather than hand-edited.
3. **Stored rows are not corrected.** Rows saved before the fix stay 5 to 6 hours early. See the questions.
4. `query-checking-data-source.ts` (the test helper): `recordWrites` now wraps the driver's real query runner so subscribers fire, and takes an optional third argument answering SELECTs.
5. Release note `docs/releases/unreleased/2584-utc-timestamps.md` (says: run the migration before the image rollout; earlier times read 5 to 6 hours early). `docs/gisday-migrations.md` gained a "Timestamps, and a database whose clock is not UTC" section on how to test this.

The normal `gisday-db` is UTC.
- **Reproduced on today's code**: an insert into `tags` read `created` = `14:33:38 +00:00` when UTC was 19:33, 300 minutes early.
- **Red first**: 3 new unit specs (`utc-timestamps.spec.ts`, 4 tests; `submission-timestamps.spec.ts`, 3 tests) against today's code: 7 failed (update SQL was `"updated" = CURRENT_TIMESTAMP`; inserts had no date parameters; defaults `getdate()`; competition `created` undefined). The migration ran on the Central DB: 68 `sysdatetimeoffset`, 0 `getdate`; a second `migration-generate` said "No changes in database schema were found" (no drift). The old code's inserts now get the true instant from the default. **Caveat:** the old code's updates still write `CURRENT_TIMESTAMP` (local time, `+00:00`), so updates stay wrong until the new image is rolled out.
