## 1. What changes in `build.yml`

One step, same folder, same name:

```yaml
      - task: PublishPipelineArtifact@1
        inputs:
          targetPath: $(Build.ArtifactStagingDirectory)
          artifact: 'js-monorepo-${{parameters.buildType}}'
        displayName: 'Publish Artifacts'
        condition: and(succeeded(), eq(variables['IS_DEPLOYABLE'], 'True'))
```

Notes from the documentation:
- `pathToPublish` becomes `targetPath`; `artifactName` is accepted as an alias of `artifact`. `targetPath` accepts variables but **not wildcards**, so the `CopyFiles@2` step stays (it is what brings `package.json` and `package-lock.json` in beside `dist`).
- `publishLocation` defaults to `pipeline`; do not use `filepath`.
- Names may not contain `\ / " : < > | * ?`; `js-monorepo-development` is fine.
- Pipeline artifacts honour a `.artifactignore` inside `targetPath`, and with none present skip `.git`. The staging folder has no `.git` and no `node_modules`, so nothing changes in what is uploaded.
- The step works on both pools (it needs the pipeline artifact service, which the Linux-Build lab agent reaches the same way it reaches build artifacts; I could not confirm this from the documents alone, so the dev check below covers it).
- Run deletion deletes the artifact with it (same as now). Pipeline artifacts are exempt from storage billing.
- **Do not publish both types under the same name for one build.** I could not find a statement that this is allowed, and a duplicate name is the likely failure. If both are wanted at once, give the new one a different name (see 3).

## 2. What the maintainer changes in release definition 13

A classic release can link any pipeline artifact: the doc says *"You can link your Classic release pipeline to any pipeline artifact"* and lists artifact download, auto-trigger and the artifact variables as working for the Azure Pipelines source. The linked item is the **build pipeline** (the source and its alias), not the artifact type, so in the expected case **nothing in the artifact source needs changing** if the artifact name and the layout stay the same. The maintainer should check, in the release editor, and only edit if a check fails:

1. The artifact source: **Source (build pipeline)** is this repository's pipeline, and **Source alias** is unchanged. The stage's file paths (`$(System.DefaultWorkingDirectory)/<alias>/js-monorepo-<type>/dist/apps/aggiemap-angular` and so on) are built from the alias and the artifact name. Keep both and no task changes.
2. If any stage has a **Download Pipeline Artifact** or **Download Build Artifacts** task in place of the automatic download, it must be a task that can read the new type: use *Download Pipeline Artifact* (and then the path it downloads to is a destination the task sets, check it matches). A *Download Build Artifacts* task reads only build-type artifacts and would fail on the new one.
3. The **continuous deployment trigger**, if one exists, fires on a new build whatever the artifact type; the doc lists it as supported. Check the branch filter is unchanged.

Open point I could not settle from documentation: the exact download folder a classic release uses for a **pipeline-type** artifact (build-type gives `<alias>/<artifact name>`). The Microsoft pages describe `$(Pipeline.Workspace)/<artifact name>` for YAML runs and say nothing different for classic releases. The dev check (4, step 3) shows it before anything depends on it.

## 3. Switching without a gap

A single build cannot safely carry both types under one name, and the release takes whatever the **latest successful build** of the pipeline offers, so the cleanest cut is a single pull request:

1. **Before the change merges:** nothing; old builds keep their build-type artifacts, and release 13 can deploy them (an artifact source reads either type, per the doc's Azure Pipelines table). Old builds remain deployable after the switch, so rollback of a release is not affected.
2. **The pull request:** change only the one task above, name unchanged. Merge on a day the maintainer is free to run the release by hand.
3. **First build after the merge** produces the new type. If the release is auto-triggered, let it run (or create a release manually, picking that build). If the layout differs, deploying `development` fails at the copy step, which is visible and harmless (the release clears its target before copying, so the stage must not be run on `master`/production first).
4. **Rollback:** revert the one step; the next build publishes the old type again.

If the maintainer would rather overlap, publish the new type under a second name (`js-monorepo-<type>-pipeline`) from the same step for a week while release 13 still reads the old name, compare the contents, then change the release's paths and delete the old step. Costs the 8 to 9 minutes for that week and is what I would do only if the dev check fails on layout.

## 4. Checking one release end to end on dev

1. Branch from `development` with only the one-step change (`ci/2341-pipeline-artifact`), push to the **origin** repository (a fork build gets restricted tokens). The task is gated on `IS_DEPLOYABLE`, which is true only for the branch names `development` and `master`, so a test branch will not publish. Temporary options: (a) run the one build on `development` itself after merging, using the Setup stage's `IS_DEPLOYABLE`; or (b) for the test branch only, add `ci/2341-pipeline-artifact` to the `IS_DEPLOYABLE` expression and **remove it before merging**. (b) is the lower-risk way; the release does not run from a branch build unless someone picks that build.
2. Look at the run's **Artifacts** tab: `js-monorepo-development` is present as a pipeline artifact; open it and confirm `dist/apps/aggiemap-angular/...`, `package.json`, `package-lock.json`.
3. In release 13, **Create release**, choose that build for the artifact, deploy to **dev only**. In the log of the first stage, read the **Download artifact** line (it prints the destination folder and the artifact type) and compare with the path the copy task uses.
4. Open the dev site; confirm the version and the files' timestamps; compare file count with the previous release's artifact (`ls -R | wc -l` on the build agent or the Explorer of the old build's artifact).
5. Compare timings: the Publish step's duration before (8 to 9 minutes) and after, on both the lab and hosted pool. The doc does not give a speed-up figure, so measure it on one `development` build first; if it is not clearly faster, the change is not worth the risk and #2341 can close with the numbers.
6. Only then merge, and repeat 2 and 3 for `master`/production, deploying to dev again first.
