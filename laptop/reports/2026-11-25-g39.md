## The migration, `RemoveInitialSurvey1795626160254`

**`migration:generate` wrote only the column drop.** TypeORM does not drop a table that no entity names. So I wrote in the two
table drops by hand, with their three foreign keys first, as #3269's `DropSessionDetailsSends` did, and the migration's comment
says so.

`up`:

```sql
ALTER TABLE "initial_survey_responses" DROP CONSTRAINT "FK_59ca4cfb5e8ee3b3a52bbd50e2b"
ALTER TABLE "initial_survey_responses" DROP CONSTRAINT "FK_461bb54e4f9f5e55b946e4b24c0"
ALTER TABLE "initial_survey_questions" DROP CONSTRAINT "FK_bbffec509ddf4b7fe93c5b0b5f2"
DROP TABLE "initial_survey_responses"
DROP TABLE "initial_survey_questions"
ALTER TABLE "user_info" DROP COLUMN "hasCompletedInitialSurvey"
```

**`down`** puts the column and both tables back **empty**, then the three foreign keys. The tables come back with their primary-key and
default-constraint names, and with the defaults the database has today. Those are **`SYSDATETIMEOFFSET()`, not `InitialSchema`'s
`getdate()`**: a later migration changed them, and I read them from `sys.default_constraints` rather than copying `InitialSchema`.

**Run locally** on the scratch database (made-up data; 0 survey rows, 0 users with the flag), migrated to `DropSessionDetailsSends`:

| Step | Result |
| --- | --- |
| `run` | exit 0, "executed successfully". After it: 0 `initial_survey` tables, 0 foreign keys, no column |
| `revert` | exit 0, "reverted successfully". After it: both tables, all three foreign keys and the column, the same as before, read from `sys.columns`, `sys.default_constraints` and `sys.foreign_keys` |
| `run`, `revert` again | the same both times |
| **`run`, then a second `migration:generate`** | **"No changes in database schema were found"**: the entities and the schema agree |

**The scratch database is left reverted** (the migration shows as pending), so it still matches `development` for the next batch.

## Deploy order: code first, then the migration

**The API before this change reads `hasCompletedInitialSurvey` on every `user_info` query**, because TypeORM selects every column an
entity names. If the migration drops the column while that API is still running, those queries fail.

So deploy this change's API first, then run the migration. The new code is safe on the old schema, because its entities do not name the
column or the tables. The pull request body says this under "Deploy order".
