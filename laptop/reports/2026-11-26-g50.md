# g50: saving an event erases its recorded attendance (#3827)

Laptop, 26 November 2026, finished 10:30 PM Central. **Branch ready: `fix/3827-event-save-keeps-attendance`** on the fork (`c198b0333`). Its last commit is `.pr-body.md` (`Title:` and `Closes #3827`), and the branch is merged with today's `development`.

## The fault, and which half was fixed
- **Where.** `event-add-edit-form.component.ts`, `payload()`. The form sends every control it holds.
- **Why.** The two counts are `select: false` on the `Event` entity, so `GET /api/events/:guid` never returns them. The form therefore opened with its Attendance boxes empty and sent both as `null`, and `EventProvider.updateEvent` spreads the body over the stored event.
- **Fixed in the form.** It now reads the counts from `GET /api/events/:guid/attendance`, the route the session page already uses. It shows them, and leaves them out of a save until it has read them. That is the pattern it already uses for the judges (#3183). It sends them as whole numbers, with an empty box as none.
- **The API is unchanged.** Its update writes only what it is sent, which is right. Making it ignore the counts would have left the form's Attendance boxes empty and unable to save.
- **The session page's own attendance save** still works: PATCH attendance 200, and the database holds 12 and 15.

## Specs
- **Form, red first:** 4 new tests. All four failed on the unfixed form: it never asked the route, opened without the counts, sent them before reading them, and sent typed counts as text. Fixed, the form's 35 pass, and the library's 359.
- **API, a guard:** an update that does not send the counts saves an entity without them. It passes before and after, since that half was already right; it is there to keep the contract. The event API's 106 pass.
- An API spec cannot be red here: the specs' data source builds SQL and never connects, so it cannot store 12 and 15 and read them back. The end-to-end proof is the database readings below, through the real API.

## For the maintainer: has production already lost attendance?
**The data cannot say for certain.** An erased count and one never recorded are both NULL: an event created in the admin form with empty boxes is saved NULL as well, and one made otherwise starts at the column's default, 0.

**What it can do is list where a loss was possible.** That means NULL counts, the event edited after its day, and people at it (check-ins or RSVPs). An event with NULL counts that was never edited after its day cannot have lost them this way.

**The certain answer is a backup.** Any event whose counts are numbers in a backup taken before its last edit, and NULL now, lost them; the backup also gives back the numbers.

The query, read-only, run only on my local scratch database. It is also at `C:\TAMU\laptop-tools\g50\attendance-possibly-erased.sql` on the laptop:

```sql
-- #3827: GIS Day events whose observed attendance may have been erased by an admin edit. READ-ONLY: it changes nothing.
--
-- The data cannot tell an erased count from one never recorded: both are NULL (an event created in the admin form with
-- its boxes empty is saved NULL too, and one created otherwise starts at the column's default, 0). So this lists the
-- events where an erasure is possible and worth checking: NULL counts, the event edited ("updated") after its day, and
-- people at it (check-ins or RSVPs). An event whose counts are NULL and that was never edited after its day cannot have
-- lost them this way. The certain answer is a comparison with a backup taken before the edits: any event whose counts
-- are numbers there and NULL here lost them.
SET NOCOUNT ON;

SELECT
  s.year,
  d.date                                   AS day,
  e.name,
  e.guid,
  e.observedAttendeeStart,
  e.observedAttendeeEnd,
  e.updated                                AS lastEdited,
  (SELECT COUNT(*) FROM checkins c WHERE c.eventGuid = e.guid)    AS checkIns,
  (SELECT COUNT(*) FROM user_rsvps r WHERE r.eventGuid = e.guid)  AS rsvps
FROM events e
JOIN seasons s ON s.guid = e.seasonGuid
LEFT JOIN seasons_days d ON d.guid = e.dayGuid
WHERE e.observedAttendeeStart IS NULL
  AND e.observedAttendeeEnd IS NULL
  AND d.date IS NOT NULL
  AND e.updated > DATEADD(day, 1, CAST(d.date AS datetime2))
  AND (EXISTS (SELECT 1 FROM checkins c WHERE c.eventGuid = e.guid) OR EXISTS (SELECT 1 FROM user_rsvps r WHERE r.eventGuid = e.guid))
ORDER BY s.year DESC, d.date, e.name;

-- And, for scale: how many events of each season hold counts at all, are NULL, or are 0.
SELECT
  s.year,
  SUM(CASE WHEN e.observedAttendeeStart IS NOT NULL OR e.observedAttendeeEnd IS NOT NULL THEN 1 ELSE 0 END) AS withCounts,
  SUM(CASE WHEN e.observedAttendeeStart IS NULL AND e.observedAttendeeEnd IS NULL THEN 1 ELSE 0 END)         AS bothNull,
  SUM(CASE WHEN e.observedAttendeeStart = 0 AND e.observedAttendeeEnd = 0 THEN 1 ELSE 0 END)                 AS bothZero,
  COUNT(*)                                                                                                   AS events
FROM events e
JOIN seasons s ON s.guid = e.seasonGuid
GROUP BY s.year
ORDER BY s.year DESC;
```

On the local copy it ran cleanly and listed 11 candidates. That copy's edit dates are mine and the restore's, so its rows say nothing about production. It also shows how common NULL counts are on any copy: 2025 has 77 events with counts and 37 with both NULL; 2024, 17 and 70.
