## The refusals with a reason cannot be shown with today's API

- **The new code only shows a reason for a 4xx.** `serverMessage` reads the API's message only for a 4xx. #3382's pin spec
  proves the reason with a made-up `422`.
- **Place: refused for real, but with a 500.** A made-up broadcast was put on a made-up place (`event_broadcast.placeGuid` has no
  cascade), so the place's delete was refused by the database. The API answers that with **500 "Could not delete entities."**, so the
  page shows the same fallback before and after. That is correct, and it is the image's third row.
- **Speaker: could not be refused at all.** Every table that points at a speaker cascades or is cleared by the API first, so
  a made-up speaker with a session and a file **was deleted**. That was in my first try, which also deleted a made-up place before I
  found the broadcast route; both were made up, and re-seeded.
- **No place or speaker delete answers with a reason today**, so the new message cannot appear until one does. A refused
  delete that says why, for example "This place is used by 1 broadcast", would be a small API follow-up. **Not filed**; the release entry
  says what the page shows now.
