## 3. #545, the VGI export, streamed (option B)

- **Route:** `GET competitions/export/zip` (`update:competitions`, as #650's routes). It covers the active season, or the GIS Day season
  `seasonGuid` names. It is declared before `:jobId`, which would otherwise take "zip" for a job id. It answers 404 for a season
  with no VGI competition or no submissions, rather than sending a zip with a CSV of headings.
- **Reuse, not copies:**
  - #3185's `zipOfFiles` now ends in a shared `streamedZip(zip, name)`, exported from the platform API, which the VGI
    route uses too.
  - #650's query, row, photo path and CSV are moved out of its processor into `export-contents.ts`. Both the processor and
    the new route use them, so the two write the same file. The processor's behaviour is unchanged, its photo count included.
- **Page:** Admin > VGI Competition > Submissions has **Download all as a zip** beside Publish to ArcGIS. It shows "Preparing the
  zip…" while it waits, and "This season has no VGI submissions to export." on a 404. It saves through the shared `downloadFile`.
- **Proven in the browser, signed in:**
  - **The download:** the button downloaded a real zip, 7,280 bytes: `submissions.csv` (17 rows, one per made-up
    submission) and 9 photos under `medias/<submission>/images/`. The CSV's columns are #650's, then the form's answers.
  - **Data:** 9 one-pixel made-up PNGs on 6 of the scratch database's 17 made-up 2026 submissions, which had none.
  - **Requests:** only GETs were made.
- **Red first** (`6d44cf15e`): the page's 2 tests failed (no button), and the API spec did not compile (`zipForSeason` did not
  exist, and the constructor took 2 arguments, not 5).
- **One test fix after red** (`eb347716e`): the spec read the stream with `for await`, which JSZip's node stream does not
  support. It now reads by events. That was the spec's fault, not the code's.
- **Checks:**
  - **Full affected check** (`CHECK_PARALLEL=4`, nothing else running): exit 1. `gisday-angular:build-app`,
    `gisday-competitions-data-api:test` and `gisday-platform-data-api:test` failed. Jest workers were SIGKILLed, two of mine
    failed on the stream above, and one untouched platform test (`refuses an admin without update:competitions`) timed out
    at 9.5 s. Every other affected project passed.
  - **Those three, one at a time** (`CHECK_PARALLEL=1`): **exit 0**, lint, test and build, with every lint.yml step.
  - So every affected project has passed, though not in one run. **The memory kills now happen with nothing else running**, at
    `--parallel=4` and 16 GB, on the same three projects each time. This machine's full checks need `CHECK_PARALLEL=1` for them.
- **What could be removed once packages may change:**
  - From `package.json`: `@nestjs/bull`, `bull`, `@types/bull`, and `fs-extra` if nothing else uses it.
  - In the API: `export.processor.ts`, `initiateExport`, `getExportStatus` and `getExportFilePath` in `export.service.ts`, the
    `POST`, `:jobId` and `:jobId/download` routes, `export.dto.ts`, and the `BullModule` registrations in both app modules.
  - Redis would then be needed by nothing, and so would the `REDIS_*` settings.
- **Memory:** the zip holds a season's photos while it is built, as #650's did. A season of a thousand or so phone photos,
  which are shrunk before upload (#1787), is tens of MB. Not measured with real photos.
