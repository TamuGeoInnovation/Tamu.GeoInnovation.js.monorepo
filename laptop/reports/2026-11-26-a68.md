## What this changes

On the Break / Summer and New Student Conference parking maps, a lot's copied link (`?feature=<layer>:<object id>`) opened the map with nothing selected. It now opens zoomed to the lot, with that lot's popup.

**Which half was broken.** Not the link. Asked of the service, lot 100e's `26118` in the issue's link is the lot's own `GIS.TS.ParkingLots.OBJECTID`, and so is 100g's `26116` (production) and `34768` (development). The link's reader found the lot by that id, but both services answer `query` with each lot's attributes and **no geometry**, whatever is asked (`returnGeometry=true`, `outSR=4326`, `f=geojson`): the fault recorded in #2520. `EsriMapService.selectFeatures` then read `ft.geometry.type` on a null geometry and threw, and `EventService` logged it and moved on.

**The fix, in the shared place.** `find` and `identify` on the same MapServer do return the lot's polygon. So `EventService.selectFeatureByObjectId`, which every event map's `feature=` link and search-result selection goes through, now asks the layer's MapServer `find` for the geometry when a found feature has none, by its object id field, exactly. A layer that is not a map service, or a `find` that fails, leaves the feature unselected as before, without the throw. `find` is added to `EsriModuleProviderService`'s modules.

The copy control writes the link with the map's own address and layer id (`event-share-url.ts`), and it is shared by every event map's markdown popup; it needed no change.

**What this does not fix.** Clicking a lot on these two maps still never reaches their lot layer, because the view cannot hit-test a feature it has no geometry for (#2520, still listed in `allowedPopupFailures`). That needs Transportation to republish the layers.
