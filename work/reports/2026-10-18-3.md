## Follow-up: the three run alone against both environments

The maintainer chose decision 2A, so the three tests were run **alone**, one worker, from the same
worktree at `86893756c`, against dev and against production, within twenty minutes of each other.

Running them against two *commits* was the original suggestion and it does not work: dev serves one build
at a time, so a spec from an older worktree would run old test code against the new app. And
`popup.spec.ts:109` does not exist at `f800c2edf` — it arrived with #1866. Dev against production is the
comparison that holds, because only the deployed app differs.

| Test | dev (`86893756c`, ArcGIS 5.0.19) | production (`264eebb42`, ArcGIS 4.34) |
| --- | --- | --- |
| `popup.spec.ts:109` | passed first attempt, 1.3m | passed first attempt, 1.1m |
| `perspective.spec.ts:92` | passed first attempt, **5.5m** | passed first attempt, **2.0m** |
| `basemap-zoom.spec.ts:24` | passed first attempt, 1.9m | **failed all three attempts** |

**The two that mattered are contention, not this build.** Both have failed their first attempt in every
tier today — two of two, and three of three — and both pass first time with the machine to themselves, on
**both** app versions. Neither ArcGIS 5.0, nor OnPush, nor the signal conversions caused them. That is
[#1716](https://github.com/TamuGeoInnovation/Tamu.GeoInnovation.js.monorepo/issues/1716). It is also what
makes `dev-2026-10-18-2` sound: nothing in the build is behind them.

**Two issues came out of it, both filed with every field set:**

- **[#1889](https://github.com/TamuGeoInnovation/Tamu.GeoInnovation.js.monorepo/issues/1889), Medium** —
  going to 3D on the vector basemap takes 5.5 minutes alone against 2.0 on the raster one. Part of the gap
  is scope, since production does not offer the vector basemap, and that is the point: the extra work *is*
  the vector basemap. A path needing five and a half minutes alone has nothing left when it shares a
  machine. It may not be ours to fix:
  [#1741](https://github.com/TamuGeoInnovation/Tamu.GeoInnovation.js.monorepo/issues/1741), republishing
  the cache in Web Mercator, removes the stand-in basemap that is the likely cause.
- **[#1890](https://github.com/TamuGeoInnovation/Tamu.GeoInnovation.js.monorepo/issues/1890), High** — the
  production failure above is **not production's fault and not contention**. `basemap-zoom.spec.ts` waits
  for `arcgis-zoom calcite-button[icon-start="plus"]`, ArcGIS 5.0's web-component zoom widget; production
  runs 4.34, where it is `.esri-zoom .esri-widget--button`. The selector changed with the 5.0 step, so the
  suite on `development` cannot pass against production until production is on 5.0 — and **step 5 of the
  release sequence is to run this tier against production after a deploy.** The message points at the zoom
  widget, so it reads as though production is broken.

**A correction recorded on #1849:** a status note there said all three passed alone, written when five of
the six runs had finished. The sixth failed. The conclusion about the first two is unchanged; the third
