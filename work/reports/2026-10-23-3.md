## The decision worth explaining: the comparison is not in YAML

A comparison written in a workflow can only be tested by pushing a branch and waiting for a schedule,
so in practice it is never tested. And the failure mode is silent - **a gate that lets everything
through looks exactly like a gate with nothing to catch.** So the deciding is in `tools/`, as pure
functions over plain data, and `tools-tests.yml` already runs `node --test 'tools/**/*.test.mjs'` on
any pull request touching `tools/`, so it needed no new CI wiring.

**Proven by mutation, not just by passing.** Changing `keyOf` to match on the advisory id alone -
ignoring which package it is in - turns the suite red with the message it was written for:

```
AssertionError: the same CVE on another package was treated as accepted
```

That is the case that matters: one CVE lands on several packages in an image (OpenSSL's appear against
`libcrypto3` and `libssl3` alike), and accepting it for one must not silently accept it for the other.
Restored, 11 tests pass - 8 new, 3 pre-existing.

## The publish gate

`publish.yml` had one `build-push-action` doing both. It now builds with `load: true, push: false`,
scans that local image, and only then runs the original push step - which is unchanged and reuses the
layers already built, so it publishes rather than rebuilding.

- **Before the push**, because a critical that reaches the registry can be deployed, and this pipeline
  cannot pull a tag back.
- **Critical only.** High is reported daily; blocking on it would stop every publish over findings
  already tracked and accepted - 28 of them today.
- That job has **no checkout** (its workspace is the build artifact), so the accepted file and the
  checker are fetched by a sparse checkout into `.security-gate/`, where they cannot collide with it.
- Trivy is pinned to **0.76.1** in both workflows. A gate whose scanner changes under you reports
  different things on different days for the same image.
