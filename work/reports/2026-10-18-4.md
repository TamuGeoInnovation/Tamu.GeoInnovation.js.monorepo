### Where this differs from the batch, and why it matters

The batch asks for **three attempts per test per commit with `--retries=0`**, from worktrees at
`f800c2edf` and `86893756c`. What ran was **one run per test per environment with the default retries**,
started before batch 4 existed, from the `86893756c` worktree only.

So:

- **These are not failure rates.** One first attempt each. They show that a first attempt alone succeeds
  where a first attempt under six workers fails; they do not show how often it would fail alone.
- **The two-commit half was not run**, and two things stand in its way. Dev serves one build at a time, so
  a spec from an older worktree runs old test code against the new app — which the batch now says itself.
  And `popup.spec.ts:109` **does not exist at `f800c2edf`**; it arrived with #1866 in `3cb5b6fdb`, so only
  two of the three can be run from that commit at all.
- **What was run instead compares app versions**, dev against production, which is the comparison the
  deployed environments actually offer. It is what produced the two issues below.

The three-attempt version has not been run and is a few minutes per test if it is still wanted.

### `basemap-zoom.spec.ts` against production is not a speed result

It failed all three attempts waiting for `arcgis-zoom calcite-button[icon-start="plus"]`, ArcGIS 5.0's
web-component zoom widget. Production runs 4.34, where that widget is `.esri-zoom .esri-widget--button`.
The selector changed with the 5.0 step (#1859, #1861), so a spec from `development` cannot pass against
production at all. Filed as
[#1890](https://github.com/TamuGeoInnovation/Tamu.GeoInnovation.js.monorepo/issues/1890), **High**, because
step 5 of the release sequence runs this tier against production after a deploy and the failure reads as
though production's zoom widget is broken.
