## 1. Crashes since 14 October: none

**Every pod reports `restartCount: 0`**, so there is no `lastState.terminated` to read on any of them, and no
exit 139 or 134 anywhere. The `geoservices-nest` pods have run unrestarted since 27 August - 57 days - which
is strong evidence against a crashing exploit attempt on that API specifically, because a segfault would have
shown as a restart and the counter has not moved.

The two `gisday-nest` pods were recreated on 22 October at 20:56 UTC, which is a deployment, not a crash
(both pods, new ReplicaSet hash, zero restarts since).

## 2. API logs: nothing matched, and nothing could have

Scanned for `brotli`, `BROTLI_DECODER`, `Z_DATA_ERROR`, `Decompression`, `incorrect header`,
`heap out of memory`, `Segmentation`, `Content-Encoding`. **0 matches in all five pods.** No `--previous` logs
exist, because nothing restarted.

**But the logs are startup-only**, which is why that zero means very little:

| Pod | Lines | First | Last |
| --- | --- | --- | --- |
| `gisday-nest` (gisday) | 335 | 22 Oct 20:56:55 | 22 Oct 20:59:18 |
| `gisday-nest` (ucgis) | 245 | 22 Oct 20:56:12 | 22 Oct 20:56:54 |
| `geoservices-nest` | 11 | **27 Aug 05:48:41.438** | **27 Aug 05:48:41.481** |

The geoservices API has written **eleven lines in 57 days, spanning 43 milliseconds**. These APIs do not log
requests at all, so an exploited request would leave no line to find.

## 3. Ingress: 22 hours of coverage, no headers, no client addresses

`rke2-ingress-nginx-controller`, two pods in `kube-system`. Combined coverage **22 Oct 13:14 UTC to now** -
roughly 22 hours. **Nothing covers 14 to 21 October.**

**3,049 requests to the three NestJS backends** in that window:

| | |
| --- | --- |
| GET 304 | 2,090 |
| GET 200 | 822 |
| GET 404 | 81 |
| PATCH 200 | 26 |
| POST 201 | 12 |
| GET 504 | 8 |
| DELETE 200 | 4 |
| GET 499 | 4 |
| POST 403 | 1 |
| GET 401 | 1 |

**No 400, 413 or 415 at all** - the statuses a malformed or oversized compressed body would most likely
produce. The 8 timeouts and 4 client-aborts are all on the geoservices API, scattered across the window with
six of them between 08:13 and 08:18 on 23 October; that reads as slowness, not as a burst, but it is the only
cluster of anything in the window.

Two limits on this section:

- **The log format records no request headers**, so `Content-Encoding: br` is invisible to it. Confirmed by
  searching the whole log for the string: it does not occur once.
- **The client field holds one value for all 3,049 requests** - the proxy in front of the ingress. Real client
  addresses are not recorded, so "a burst from one address" cannot be assessed at all.
