## Batch 7 — #1867: why that campus map never finished drawing

**It is ArcGIS 5.1. It is not that campus's services.**

| Run | ArcGIS | Result |
| --- | --- | --- |
| dev, `one "dc-bush-school" --retries=0` | **5.1** | **failed** — 9 passed, 1 failed |
| dev, again | **5.1** | **failed** — same test |
| production, same command | **4.34** | **10 passed**, `popup.spec.ts:79` among them |

No retries anywhere, so every attempt counted.

**The control is better than it looks.** `dcBushSchoolBasemapUrl` and `dcBushSchoolFeatureServerUrl` are
fixed to `gis.tamu.edu` in `connections.ts` and do not resolve per environment, so **both environments
draw this campus from the same services and the same data**. Same machine, same minute. The only
difference between the passing run and the two failing ones is the ArcGIS version. That rules out #1247,
#1464 and #1248, and leaves 5.1 under software WebGL — what #1867 and #1897 warned of.

### What the view does

Probe on dev, every 10 seconds for three minutes:

```
  11s  ready false  drawing true
  21s  ready true   drawing true
  ...
  91s  ready true   drawing true
 101s  ready true   drawing false   <- stops here
 181s  ready true   drawing false
```

**`drawing` stays true for about 100 seconds**, then stops and stays stopped. The map does finish; it is
late. `ready` is true at 21 seconds, so layers settle early and the **painting** runs long, which is a
software-WebGL shape rather than a service one. No request failed or hung — the only two failures in
three minutes were Google Analytics beacons aborting, which is the suite's own blocking.

### What batch 7 asked for and this did not deliver

**Which layer holds the view.** The probe reported **no layers at all, `0/0` at every sample**, so it
cannot name one. Either the probe is not wired for the campus maps or their layers are registered another
way. Reading that as "the campus map has no layers" would be wrong: the map draws.
