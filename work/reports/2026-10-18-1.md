### The two flaky tests

Both failed once and passed on retry, and neither looks like an ArcGIS 5.0 fault from this run. Both
are the 180-second timeout running out, which is
[#1716](https://github.com/TamuGeoInnovation/Tamu.GeoInnovation.js.monorepo/issues/1716).

**`basemap-zoom.spec.ts`, the basemap at the deepest zoom.** Two first-attempt timeouts: `locator.count`
at `paint.ts:151`, and `locator.click` waiting for the zoom widget. The call log says the opposite of what
a 5.0 break would:

```
waiting for locator('arcgis-zoom calcite-button[icon-start="plus"]')
  - locator resolved to <calcite-button ... class="zoom-in" title="Zoom in" ...>
  - attempting click action
  - waiting for element to be visible, enabled and stable
```

The selector **found** 5.0's web-component zoom widget. It timed out waiting for it to settle, not for it
to exist. This test is the usual casualty on a loaded machine, and the handoff page already lists it as
such.

**`perspective.spec.ts`, 3D on every campus basemap.** First attempt: *"3D from Aggieland vector,
September 2026: 3D is not a Web Mercator globe with its 3D buildings"*, then passed. The scene had not
finished reprojecting inside the window rather than having come up wrong.

By layer: neither failure was a layer failing to load or serve data. Both were the browser not reaching a
settled state in time.

## Decisions for the maintainer

**1. The run took 41.6 minutes against about 30 for the last two release tiers**

Same tier, same machine, 548 tests against 549 on 16 October, so the suite did not grow. The first run on
a new ArcGIS major is a reasonable explanation; so is machine load. This run cannot tell them apart, and it
matters beyond this release: the nightly full run is already being cut off by its two-hour cap
([#1748](https://github.com/TamuGeoInnovation/Tamu.GeoInnovation.js.monorepo/issues/1748)), and a third
more time per test would make that worse.

- **A. Wait for the next release tier and compare before filing anything ← recommended** (one more
  measurement separates "first run on a new major" from "5.0 is slower", and costs nothing extra)
- B. File an issue now to measure it properly: the same tier on `dev-2026-10-16` and on `dev-2026-10-18`,
  back to back on a quiet machine.
- C. Treat it as noise and move on.

**2. `AZURE_DEVOPS_PAT` is missing on the work machine**

- **A. Add the read-only PAT to this machine as a user environment variable ← recommended** (it is what
  the batch template assumes, and it is read-only)
- B. Change the task template to identify builds from the deployed bundles, as this report did, and drop
  release numbers from work-machine reports.
- C. Leave it; the home session supplies the build number when it writes each batch.
